# PI Harness 架构设计

## 1. 目标

PI Harness 是本地优先的 Agent Harness：浏览器提供 Codex 风格界面，本地 daemon 负责模型调用、Agent 运行、工具执行、安全审批和持久化。

底层只复用：

- `@earendil-works/pi-agent-core` 的 `Agent` 与 Agent Loop。
- `@earendil-works/pi-ai` 的模型、Provider、流式调用与认证能力。

Session、事件协议、工具、Skill、权限、Sandbox、记忆、上下文管理、Planner、持久化和观测由项目自己实现。不使用 Pi 内置 `AgentHarness`、Coding Agent Session、工具、Session Storage 或完整 Harness。

### 能力范围

| 能力 | 所属模块 | 关键约束 |
|---|---|---|
| Provider / Model | `providers` + daemon provider service | 复用 `pi-ai Models`，内置按需注册，自定义配置可持久化 |
| Tool/Skill Registry | `packages/tools/src/lib/tool-registry.ts` / `packages/tools/src/skill-registry.ts` | 稳定 ID、schema、来源和权限分类校验 |
| MCP Client + Host（待实现目标） | daemon MCP 模块 + tools 适配 + policy + agent-runtime + Web feature | 完整目标、任务状态和验收见 [MCP 实施台账](./mcp-client-host-plan.md)；复用现有执行链，不对外提供 MCP Server |
| Tool/Skill 选择 | Tool Selector / Skill Registry | Tool 候选可按需缩小；Skill 由模型根据元数据选择，不授权 |
| Tool 并发、超时与去重 | Tool Execution Guard | 只读可并行，写入/Shell 串行 |
| Sandbox | `sandbox` | workspace、进程、资源和网络边界 |
| Memory / RAG | daemon memory，后续可提取 `retrieval` | 记忆可审计，索引可重建 |
| Context 压缩 | `agent-runtime/context` | 不覆盖原始 JSONL |
| Planner / Todos | `tools/tools/planner.ts` / `todos.ts` | 作为控制工具维护规划与执行状态 |
| Policy | `policy` | 统一 `allow / ask / deny` |
| Human-in-the-loop | daemon + runtime + policy | 可持久化、可超时、可恢复 |
| Trace | daemon observability | 关联 run/model/tool/retrieval/HITL，写入前脱敏 |

## 2. 总体架构

```mermaid
flowchart LR
    Web["React Web"]
    Daemon["Fastify Local Daemon"]
    Runtime["Agent Runtime"]
    Core["pi-agent-core<br/>Agent Loop"]
    Providers["Provider Runtime<br/>pi-ai Models"]
    AI["pi-ai"]
    Policy["Policy / Approval"]
    Tools["Tool Registry"]
    Sandbox["Sandbox"]
    Store["SQLite + Session JSONL"]
    Workspace["Workspace"]

    Web -->|"HTTP / SSE"| Daemon
    Daemon -->|"command"| Runtime
    Runtime -->|"HarnessEvent"| Daemon
    Runtime --> Core
    Runtime --> Providers
    Providers --> AI
    Runtime --> Policy
    Runtime --> Tools
    Tools --> Sandbox
    Sandbox --> Workspace
    Daemon --> Store
```

项目是 pnpm workspace 管理的 TypeScript Monorepo，运行时仍是模块化单体：只有一个 daemon 进程，不拆微服务。

### 边界

- Web 只负责交互，不持有凭据，不访问本地文件，不导入 Pi、daemon storage 或 tools。
- daemon 是组装根，负责 HTTP/SSE、业务服务、持久化和运行时组装。
- `agent-runtime` 只编排 Agent，不直接实现 SQL、HTTP、SSE 或文件工具。
- Pi 原始事件只能在 `agent-runtime` 内出现，对外必须转换为 `HarnessEvent`。
- Policy 决定“能否执行”，Sandbox 限制“最多能影响什么”，两者不合并。

## 4. Agent 运行时

每个 session 对应一个 `Agent`：daemon 保存 `Map<SessionId, AgentRuntime>`。一个 session 同时只允许一个活动 run；同一 workspace 的不同 session 可以并发运行，写入冲突由副作用工具在执行前复查目标状态并拒绝旧写入。

`agent-runtime` 负责：

- 根据 session 消息、Provider、Model、Tool 和 System Prompt 创建 `Agent`。
- 调用 `prompt()`、`continue()`、`abort()`、`steer()` 和 `followUp()`。
- 使用 `beforeToolCall` 接入 Policy 与审批，使用 `afterToolCall` 发出审计和文件变化事件。
- 使用 `transformContext` 实现上下文预算、裁剪和压缩。
- 订阅 `Agent.subscribe()`，把 Pi 事件转换为项目事件。
- 无工具任务需要跨模型轮次自主迭代时，`prompts/auto-follow-up-prompt.ts` 维护续轮提示词和标记，`utils/auto-follow-up.ts` 维护消息检测与标记清理，`auto-follow-up.ts` 创建每个 run 独立的续轮处理器并封装续轮上限；Runtime 在 `message_end` 后通过 `followUp()` 注入内部用户消息，最多自动续轮 8 次。内部消息写入 Session JSONL 以保证恢复上下文，但 Web 不渲染。
- `prompts/rich-content-prompt.ts` 维护 Web 可渲染的图表、公式和线性流程块输出协议，`system-prompt.ts` 只组合独立提示词片段。

Agent 恢复流程：

```text
SQLite 读取 session 元数据
→ JSONL 恢复完整 messages
→ 解析 Provider / Model
→ 组装 System Prompt / Skills / Tools / Context
→ 创建 Agent 并订阅事件
→ 放入 AgentManager
```

用户发起 Run 或 Follow-up 时使用结构化 `RunUserInput`，由普通文本、附件和 `@` Workspace 引用组成。Web 的文件选择与输入框文件粘贴复用同一套附件校验和序列化链路；daemon 在 API 边界限制数量、名称、大小和引用类型，Runtime 在真正读取前再次执行 Workspace 真实路径和受保护目录检查，再组装标准 `UserMessage`：

运行期间输入器按 daemon `app_settings` 中的繁忙发送偏好调用 `followUp()` 或 `steer()`：排队消息由 Runtime 持有完整结构化输入，Web 在输入器上方以紧凑、无独立卡片底色的滚动列表读取，并允许按 ID 编辑正文、删除或“调整方向”。插话与“调整方向”先由 Runtime 暂存完整消息并中止当前模型响应、工具执行或审批等待；当前 Agent 调用结束后再写入 Agent 原生 steering 队列，Runtime 不发出中间 `run.aborted` 终态，而是在同一个 Run 内通过 `continue()` 立即消费。Cmd/Ctrl+Enter 临时使用另一种行为。队列进入 Agent 时由 `message.started` 中的 `queuedInputId` 驱动 Web 移除，不把队列另存进 SQLite。

用户提交普通消息后，Web 在将该消息乐观写入 TanStack Query 缓存的同一帧，就在会话消息列表末尾追加蓝色 `TextShimmer` 文字“正在处理…”；收到 `run.started` 后由真实活动 Run 的消息投影接管，并跟随最新消息滚动，Run 进入完成、失败或中止终态后立即隐藏。该文字是全局运行反馈，不替代消息链中的思考、工具、审批或人工输入状态。

空闲时改写当前分支最后一条用户消息会追加 `message.branch_started`，JSONL 保留原始事件，但 Session 恢复、搜索、上下文和 Web 消息列表只折叠当前有效分支。Runtime 随后以改写后的完整用户消息启动新 Run，保留该消息已展开的附件和引用上下文。

- 图片附件与图片引用作为模型图片内容发送；模型不支持图片输入时明确拒绝，不静默退化。附件或引用准备失败时，仍先保存用户原始文本、附件元数据和引用元数据，再记录 Run 失败，使消息可恢复和编辑。
- 所有普通文件都允许作为附件提交，不在 Web 以扩展名白名单拒绝。UTF-8 文本直接以有界文本段加入当前用户消息；PDF、DOCX/XLSX/PPTX、ODF、RTF 与 EPUB 等常见文档由 Runtime 在本地提取文本；无法安全解析的其他二进制文件保留名称、MIME 类型和大小，并明确标记正文未展开，不能把任意二进制或 Base64 原样注入模型 Context。Workspace 文件引用复用同一解析与降级策略；文件夹引用只加入有界目录清单，不递归注入全部文件内容。
- 单个文本来源最多读取 64 KiB；同一条消息的附件与引用文本共享基于模型窗口的输入预算，超出部分带明确标记截断。该限制只约束新加入的用户参考上下文，不替代后续针对完整 Session 历史的 Context 裁剪与压缩。
- 文档解析只处理不超过 5 MiB 的单个附件或 Workspace 文件，支持 Run 中止，并对压缩型文档设置解压总量与条目数上限；解析失败按二进制元数据降级，不暴露解析器内部错误或把失败伪装成已读取正文。
- Runtime 通过 `transformContext` 先限制历史附件、引用和 Tool 结果，再按模型窗口生成结构化 checkpoint 与最近消息投影；Tool 文本结果首次进入模型前按固定首尾预算投影，避免后续请求重写既有前缀；发生压缩时追加 `context.compacted`，原始完整消息继续保留在 JSONL。
- 附件和引用内容统一标记为不可信参考资料，不得覆盖 System Prompt、用户请求或工具/权限约束；其中出现的指令只作为待分析数据。
- `displayText`、附件展示元数据和引用元数据随完整用户消息进入 Session JSONL，用于恢复原始输入标签和图片预览；准备失败的消息只保存可恢复的原始输入与元数据，不将未校验内容注入模型。模型使用的实际内容仍保持在同一条标准消息中，不建立第二份上下文事实来源。

附件与 `@` 引用在 Context 预算、裁剪与压缩之前完成组装，因此后续 Context Pipeline 可以对一条完整用户消息统一计量和处理。

## 5. Provider

`pi-ai` 只运行在 daemon。项目不重复实现 Provider Registry 或 Model Registry；`pi-ai` 的 `Models` 是唯一运行时注册表，负责 Provider 注册、模型查询、认证解析和流式请求路由。`packages/providers` 只提供 `pi-ai` 的最小装配入口，不保存应用配置、不执行校验和持久化。

自定义模型显式保存 `reasoning` 能力，未配置时默认关闭；开启后由 `pi-ai` 按协议映射推理强度和摘要参数。

### 5.2 Provider 定义

Provider 分为两类：

- `builtin`：代码内明确支持的 `pi-ai` Provider。Provider ID 使用 `pi-ai` 的稳定 ID，例如 `openai`、`anthropic`。SQLite 只保存启用状态等用户设置，不复制内置模型目录。
- `custom`：用户创建的兼容端点。daemon 生成 `custom:<uuid>` 作为稳定 Provider ID，避免与内置 Provider 冲突；配置和模型定义保存到 SQLite，凭据单独保存。

第一版自定义 Provider 支持 `pi-ai` 已提供实现的三种协议：

```ts
const CustomProviderApi = {
  OPENAI_COMPLETIONS: "openai-completions",
  OPENAI_RESPONSES: "openai-responses",
  ANTHROPIC_MESSAGES: "anthropic-messages",
} as const;

interface CustomProviderDefinition {
  id: string;
  kind: "custom";
  name: string;
  protocol: (typeof CustomProviderApi)[keyof typeof CustomProviderApi];
  requiresApiKey: boolean;
  baseUrl: string;
  enabled: boolean;
  modelIds: string[];
  createdAt: number;
  updatedAt: number;
}
```

Provider 连接配置与模型 ID 使用独立弹窗管理，因此新建自定义 Provider 时允许模型列表为空，保存连接配置后再单独添加模型。自定义模型第一版只填写模型 ID，并使用统一的保守上下文上限与零费率。需要成本统计或逐模型能力设置时再扩展表单和存储。兼容性开关只开放已经验证且确有用户需求的字段，不接受任意对象透传到 `compat`、headers 或 Provider 请求参数。

### 5.3 创建与运行流程

daemon 启动时只创建一个 `Models` 集合：

```text
创建 CredentialStore
→ createModels({ credentials })
→ 读取 provider_settings
→ 注册项目支持的内置 Provider
→ 将自定义定义转换为 pi-ai Provider
→ models.setProvider()
→ ProviderService 持有 Models
```

启用状态是应用层设置；Provider 列表仍需读取已停用项，因此启动时注册全部受支持 Provider。Runtime 在新 run 解析模型时必须拒绝已停用 Provider。

`load-built-in-provider.ts` 只处理项目实际支持的内置 Provider ID，并通过动态导入按需加载 factory，不增加 Registry 类。

内置 Provider 的注册顺序由 `load-built-in-provider.ts` 中的有序加载表统一维护；同一服务的全球版与 CN 版必须相邻，Web 与 daemon 不再各自维护另一份顺序。`anthropic`、`xai`、`kimi-coding`、`github-copilot`、`openrouter` 和 `openai-codex` 使用其 `pi-ai` OAuth 实现。Provider 列表通过 `supportsOAuth` 告知 Web 是否显示 OAuth 登录入口，不在 Web 硬编码 Provider ID。

创建自定义 Provider 时，daemon 的 `ProviderService`：

1. 根据 `protocol` 选择 `openAICompletionsApi()`、`openAIResponsesApi()` 或 `anthropicMessagesApi()` 的 lazy 实现。
2. 根据 `requiresApiKey` 创建 API Key 认证或无凭据认证。
3. 将经过校验的模型定义转换为 `pi-ai Model`。
4. 调用 `pi-ai createProvider()`，不得自行实现协议客户端或流解析。

Runtime 启动 run 前通过 `ProviderService` 解析 Provider、Model 和认证状态，再把同一个 `Models` 的 `streamSimple.bind(models)` 与解析后的 Model 交给 `Agent`。模型接口通过 `getSupportedThinkingLevels()` 返回当前模型实际支持的 `off`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max` 子集；Session 保存经 `clampThinkingLevel()` 校准后的用户选择，默认请求 `medium`，Runtime 启动时再次按当前模型能力校准后交给 Agent。API Key 不传入 Runtime。`run.started` 记录 `providerId` 和 `modelId`。

Provider 配置、启用状态或凭据变更只影响新 run。活动 run 及其启动准备期间必须阻止修改所使用的 Provider，运行占用状态由 Runtime 提供，不在 Provider 层建立重复的占用表。

### 5.4 自定义 Provider 校验

所有创建和修改输入在 daemon route 使用 TypeBox 校验，并在 service 层执行领域检查：

- Provider ID 由 daemon 生成，用户不能覆盖；名称去除首尾空白后必须非空。
- `baseUrl` 必须是绝对 HTTP/HTTPS URL，不允许用户名、密码、query 或 fragment。
- 至少提供一个模型；同一 Provider 内 model ID 唯一。
- 协议和认证模式只接受明确支持的枚举值，不接受任意协议实现或请求头。
- 自定义 Provider 删除后，其历史 session 仍保留原 Provider/Model ID，但启动新 run 时返回 `PROVIDER_NOT_FOUND`，由用户选择替代模型。

### 5.5 CredentialStore

`apps/daemon/src/storage/provider-credential-store.ts` 实现 `pi-ai` 的 `CredentialStore`，数据写入 `.pi-harness/credentials.json`，与普通 SQLite 数据分离：

- 文件和临时文件权限为 `0600`，父目录权限为 `0700`。
- 写入采用“同目录临时文件 → fsync → rename”原子替换，不原地覆盖。
- `modify(providerId, fn)` 对同一 Provider 串行执行，OAuth 刷新必须在该临界区内完成。
- `list()` 只返回 `{ providerId, type }`，不执行外部命令，也不返回 secret。
- 文件内容和解析错误不得进入日志；损坏文件必须报错，不得当作空凭据继续运行。
- 删除自定义 Provider 时同时删除对应 credential；删除失败则 Provider 保持禁用并提示用户重试清理。

第一版文件存储依赖本机账户和文件权限保护，不宣称凭据已加密。后续接入操作系统 Keychain 时只替换 `CredentialStore` 实现，不修改 ProviderService、Runtime 或 Web API。

API Key 只允许由凭据写入和连接测试接口接收，不提供完整值读取接口。Provider 列表可返回由 daemon 生成的脱敏预览：最多保留前 4 个字符，其余字符替换为 `x`，并确保末尾至少 4 位始终被遮住。连接测试中的 Key 仅用于当前请求，不写入 `CredentialStore`。OAuth 通过 `models.login()` 和 `models.logout()` 完成，刷新由 `pi-ai` 在 `CredentialStore.modify()` 内串行处理。完整凭据不写入日志、SQLite、Session JSONL、HarnessEvent 或浏览器存储。

OAuth 登录状态仅保存在 daemon 内存中，同一 Provider 同时只允许一个活动登录，并设置 15 分钟总超时。不同 Provider 可以使用本机回调、设备码，也可以在流程中请求文本、密文、选项或手动授权码输入。daemon 将 `pi-ai` 的 prompt 转换为带一次性 `promptId` 的脱敏状态，Web 只读取提示文案、选项、授权 URL、设备码和脱敏状态，并通过独立接口提交当前 prompt 的回答；输入值不进入 SQLite、日志或浏览器存储。Web 不接收 access token 或 refresh token。取消登录、prompt 失效、超时、关闭 daemon 或关闭活动登录弹窗时必须中止网络请求、轮询、输入等待和回调等待。

### 5.6 Daemon API

```text
GET    /api/providers                         # Provider、模型、脱敏认证状态与 Key 预览
POST   /api/providers                         # 创建自定义 Provider 配置
PATCH  /api/providers/:providerId             # 修改配置或启用状态
DELETE /api/providers/:providerId             # 删除自定义 Provider
PUT    /api/providers/:providerId/credential  # 写入或替换 API Key，只返回脱敏状态
DELETE /api/providers/:providerId/credential  # 注销并删除凭据
POST   /api/providers/:providerId/oauth       # 启动 OAuth 登录
GET    /api/providers/:providerId/oauth       # 读取当前 OAuth 登录状态
POST   /api/providers/:providerId/oauth/prompt # 回答当前 OAuth 交互式 prompt
DELETE /api/providers/:providerId/oauth       # 取消当前 OAuth 登录
POST   /api/providers/test                    # 使用当前自定义 Provider 草稿测试连接
POST   /api/providers/:providerId/test        # 使用已注册 Provider 测试连接
```

配置 CRUD 与凭据写入使用独立请求，不制造 SQLite 与凭据文件之间的跨存储事务。新建流程先保存配置，再单独提交凭据；凭据写入失败时 Provider 保持“未配置”，用户可以重试，不删除已填写的非敏感配置。

创建自定义 Provider 的请求只包含非敏感配置：

```ts
interface CreateCustomProviderInput {
  name: string;
  protocol: CustomProviderApi;
  requiresApiKey: boolean;
  baseUrl: string;
  models: Array<{ id: string; contextWindow: number; maxTokens: number }>;
}

interface UpdateCustomProviderInput {
  name?: string;
  protocol?: CustomProviderApi;
  requiresApiKey?: boolean;
  baseUrl?: string;
  enabled?: boolean;
  models?: Array<{ id: string; contextWindow: number; maxTokens: number }>;
}

interface PutProviderCredentialInput {
  apiKey: string;
}
```

创建接口不接收 `id`、`createdAt` 或 `updatedAt`。凭据接口成功后不回显 `apiKey`；Provider 列表仅返回 daemon 生成的 `credentialPreview`，不返回完整值。Provider 列表使用 `isConfigured` 表示认证材料是否完整，不把它命名为 `isConnected`；Web 只在用户主动测试时调用连接测试接口。测试使用指定模型发起有超时、无重试的流式最小请求，收到首个非空响应增量后立即中止，不持久化配置、Key、测试消息或结果，也不回传凭据和远端错误细节。

Provider 表单提交的 400 参数或配置校验错误显示在表单底部；网络、5xx、模型连接测试和其他请求错误使用全局 Toast。

Provider 列表中的模型元数据同时返回 `contextWindow` 和 `maxTokens`。内置模型直接使用 `pi-ai Model` 元数据；自定义 Provider 在模型管理弹窗中逐模型配置，并把非敏感元数据保存到 `provider_settings.model_ids_json`。旧版仅保存模型 ID 字符串的记录读取时自动补入 128K/32K 默认值，下一次保存升级为对象数组。Web 不自行猜测当前模型窗口。

稳定错误码至少包括：

```text
PROVIDER_NOT_FOUND
INVALID_PROVIDER_CONFIG
BUILT_IN_PROVIDER_READ_ONLY
PROVIDER_OAUTH_NOT_STARTED
PROVIDER_OAUTH_NOT_SUPPORTED
```

Provider OAuth 登录只为拥有完整交互流程的内置 Provider 开放；登录成功后由 `models.login()` 将凭据写入 CredentialStore，移除凭据通过 `models.logout()` 完成。自定义 Provider 第一版只支持 `api_key` 和 `none`。

Web 不维护硬编码的 Provider 连接状态或模型目录。TanStack Query 以 daemon 响应为事实来源；默认模型、推理强度、输出详细程度和推理摘要方式通过 `/api/settings` 保存到 daemon 的 `app_settings`，Zustand 不复制这份服务端状态。自定义 Provider 使用通用图标，不要求加入内置 Provider ID 联合类型。

默认模型是全局的新会话默认值，不绑定 workspace，并以 `providerId`、`modelId` 和推理强度作为一项设置持久化到 `app_settings`。设置页和新会话输入器读写同一 TanStack Query；创建 session 时复制当前值。会话内切换模型或推理强度只更新该 session，后续 run 使用新配置，其他已有会话保持各自选择。模型选择始终使用 `providerId + modelId`，不能假设 model ID 在不同 Provider 间全局唯一。

新 Session 创建成功后，Web 立即进入会话页，不等待首个 Run 的受理响应。daemon 在首个 Run 启动时并行使用当前模型生成简短标题；标题请求使用低推理强度、较小输出上限和独立超时，失败时退回首条输入的紧凑截断，不阻断主 Run。Run 受理响应返回后，Web 直接更新 Query 缓存中的 Session 标题，不显示标题加载态，也不需要额外轮询或新增事件协议。后续 Run 与用户手动重命名都不会再次触发自动标题。

## 6. Tool、Skill、Policy 与 Sandbox

### MCP Client + Host（实施中）

MCP 已进入实施阶段，Client 生命周期、受控 stdio/HTTP/SSE、配置与凭据存储、能力目录和管理 API 已落地；现已接入设置中的 MCP 管理与 Agent Tools 基础调用链；完整协议交互、工具级授权、恢复和 Host 界面仍在推进。本文定义模块边界，[MCP Client + Host 实现目标与任务跟踪](./mcp-client-host-plan.md) 是目标范围、全部任务、当前任务状态和完成证据的唯一台账；其中待实现能力不代表当前项目已经支持。

PI Harness 整体承担 Host 职责。daemon 管理官方 SDK Client、stdio/Streamable HTTP transport、认证、配置和生命周期；tools 提供 ToolRegistration 与受保护 ToolRegistry 执行契约，daemon McpToolService 注入官方 SDK 调用适配；agent-runtime 在每次 Run 开始前准备并固定工具快照，继续通过现有 ToolRegistry、Policy、审批、执行保护和 HarnessEvent 完成调用。Web 只消费项目 API 与脱敏事件，不接触 MCP SDK、原始协议对象或凭据。第一版模块放在 daemon 内，不为单一消费者提前创建独立 MCP Host/Client package。

完整目标包含 Tools、Resources、Prompts、Completion、Elicitation、OAuth、旧版协议兼容，以及安全隔离、上下文预算、配置管理、人工交互、Trace 和故障恢复。可选协议扩展单列台账，未实现时不声明相应能力。协议基线、支持矩阵和 SDK 版本验证由实施台账维护。

MCP 服务器启动/连接、账号授权、具体工具执行分别经过相应授权。现有 auto_approve/full_access 不静默扩张为任意外部服务写入权限；服务端 annotations 不直接决定可信权限。资源、模板和工具结果均保留外部来源，不提升为 Host 指令或内部文件变更事件。stdio 子进程不因固定 cwd 或 Roots 自动获得文件系统隔离，完整隔离必须由 OS/容器执行器提供。

MCP 服务器配置、启用状态、信任和凭据为当前 daemon 的全局设置，所有项目共用，不提供项目选择器或绑定 API。新增和编辑界面都提供表单与 JSON 两种入口，两者编辑同一份服务器配置并共用凭据类型、私网访问和调用超时设置；表单中的服务器 ID 对应 `mcpServers` 对象的 key。保存时若 ID 已存在，daemon 在同一原子变更链中依次追加 `-2`、`-3` 等后缀。stdio 表单使用命令、每行一个参数和每行一个 `KEY=VALUE` 环境变量；JSON 使用常见的 `mcp.json` 顶层 `mcpServers` 结构及 `http`、`stdio`、`sse` 类型，并支持 stdio 的 `args` 与 `env`。解析后与通用设置合并，可原子导入一个或多个服务器。daemon 在 API 边界校验并标准化后把非敏感运行配置保存到 SQLite；从表单或 JSON 输入的 `env` 仍作为敏感材料写入独立 MCP Credential Store，不回显已有值。其余敏感材料也保存在 Credential Store；这不是在工作区生成一份可被 Agent 修改的 `mcp.json` 文件。调用与人工交互事实继续写 Session JSONL。015 migration 只移除旧的 workspace_mcp_servers 表，保留服务器、启用状态、信任及凭据。会话在下一轮准备时读取全部已启用且受信任的服务器；Client 继续按会话隔离，stdio 保持会话固定 cwd。连接测试不依赖项目，在临时目录中建立独立 Client，结束后回收连接与目录。副作用请求发出前记录执行意图，断线或重启后无确定结果的调用保持未知状态，不自动重放。项目 Web SSE 与 MCP transport 独立，浏览器断连不停止 Agent。

当前连接入口为「设置 → MCP 服务器」，使用步骤见 [MCP 使用说明](./mcp-usage.md)。服务器列表通过尾部 Switch 控制启用状态，只展示配置和管理操作，不因进入列表而连接服务器或读取能力目录；列表每页渲染 25 台，单个 daemon 最多保存 1000 台服务器。点击服务器进入详情时才请求并展示脱敏后的工具数量、工具入参/出参 Schema、资源与模板、提示词参数、服务端说明和能力声明，避免大量服务器同时连接或把全部定义装入列表响应和浏览器内存；手动操作只用于重新加载或诊断连接。消息输入器的“+”菜单在 Skills 同级提供 MCP 子菜单，只读取轻量服务器配置并展示已启用且已信任的服务器；选择后插入墨绿色 MCP 标签，作为本条消息的服务提示，不触发能力发现、不改变启用范围或跳过工具审批。Skill 标签统一改为紫色。服务器图标优先使用发现结果中通过来源与格式校验的 `serverInfo.icons`，尚未发现、缺失或加载失败时统一回退通用 MCP 图标，不根据配置名称或地址推测品牌。远程鉴权默认自动检测：首次连接成功则记录无需鉴权，401 challenge 带 OAuth protected-resource metadata 时提示浏览器 OAuth，否则提示录入 Token/API Key 请求头。OAuth 入口只在服务器已启用后开放；OAuth 使用 SDK discovery、动态客户端注册、PKCE、state、issuer/resource 校验和串行 refresh；授权小窗口复用插件 OAuth 的前端 HeroUI 启动页与结果页并展示 MCP Logo，Web 校验路由参数和轮询脱敏授权状态，只有 daemon 返回的脱敏凭据版本相对本次授权发起时发生变化才提示成功，daemon 回调只重定向前端结果页。授权状态、client 信息与 token 只在 daemon 内处理，Web 只接收鉴权类型、是否已有凭据和脱敏凭据版本。授权回调临时状态保留 10 分钟且仅存在 daemon 内存，daemon 重启后需重新发起；完成与当前配置绑定的显式 OAuth 流程时保留已有连接信任，不会把开关重新切回未启用；未获得连接信任的配置也不会因 OAuth 自动变为可信。本阶段工具调用始终走通用 `USER_APPROVAL` 策略逐次审批，Plan 未确认时禁止调用；Run 使用 64 工具/512 KiB 定义预算，冻结配置与定义并在批准后及发送前复查。来源写入 Run 工具快照与 tool.started，异常调用保留结果未知且不重试。Run 准备期间单台 MCP 服务器连接或目录发现失败时，只跳过该服务器，并通过现有 `tool.started → tool.failed` 事件链在会话和 Trace 中记录失败；不得中断仍可使用内置工具或其他服务器继续执行的整个 Run。配置判别常量从无 Node/SDK 依赖的 `agent-runtime/mcp-contract` 子路径共享，Web 不引用 daemon 或 tools 主入口。

点击 OAuth 授权即表示用户允许本次鉴权发现和授权端点访问；daemon 仍校验服务启用、配置版本和凭据版本，但不要求该配置已获得工具连接信任。同一服务器同时只保留一个前端授权窗口，流程未结束时重复点击只聚焦已有窗口。

### Tool Registry

初始 workspace 工具包含：

```text
read_file  view_image  read_document  view_pdf_page  list_files  search_text
web_search  web_fetch  edit_file  write_file  run_command
```

文件查看按内容类型拆分：`read_file` 只读取 UTF-8 文本并按行分页；`view_image` 返回经过格式、大小与 workspace 边界校验的图片 `ImageContent`；`read_document` 复用共享的 Office/PDF 文本解析能力并限制压缩条目、解压后大小与输出长度；`view_pdf_page` 只渲染指定 PDF 页面，并限制像素尺寸和编码后大小。用户消息中的外部附件与 `@文件/@文件夹/@图片` 仍在模型请求前由 Runtime 做有界 Context 组装，不改成 Tool Call。

代码探索优先使用 `search_text` 定位符号、引用和候选文件，并可一次返回少量上下文行；仅按路径发现文件时使用单次递归 `list_files` glob，不逐层列目录。不含路径分隔符的 glob 按所有目录层级匹配。候选路径明确后，同一响应并行读取所需文件的最小范围，已有未变化结果不重复读取。

网络读取按搜索与正文抓取拆分：`web_search` 只调用 daemon 配置的回环地址 SearXNG JSON API，返回可供模型引用和 Web 展示的标题、URL 与摘要；`web_fetch` 使用 Node 标准网络能力读取公开 HTTP(S) 网页、文本、JSON 和 PDF，支持按正文字符位置分页。`web_fetch` 在初始请求和每次重定向前解析并固定公网地址，拒绝 URL 凭据、本机、私有、链路本地、保留和组播地址，并限制重定向次数、解压后响应大小、正文输出长度、超时和中止信号。唯一的本机例外是配置的 Skill Gateway origin 及 `/api/skill-gateway/*` 路径；Runtime 只对此精确目标附加进程内随机令牌，任何其他本机 URL 仍被拒绝。

运行时控制工具包含 `update_plan`、`update_todos` 和 `request_user_input`，与 `read_file` 等工作区工具平级放在 `packages/tools/src/tools`。它们只更新 Harness 状态或等待用户输入，不直接访问 workspace。`update_plan` 和 `update_todos` 继续维护执行进度；计划模式（`RunMode.PLAN`）是顶层 Run 的工作模式，其中的 Markdown 计划书是独立任务契约，不复用这两个工具的结构化状态。

Registry 保存稳定的工具 ID、schema、描述、权限分类、来源和执行模式。注册时拒绝重名 ID 和无效 schema；run 开始后固定当次使用的工具定义，避免执行中改变语义。

可选 Computer Use 由 `packages/computer-use` 提供 `computer_observe` 与 `computer_act`。观察结果是一张可选 PNG `ImageContent` 加一份带元素编号、逻辑坐标和 `observationId` 的 Accessibility Tree，不传输视频流。动作只接受所属 Session scope 的最新观察，前台应用变化、观察过期或坐标越过已观察窗口时拒绝。两类工具都使用 Policy 的通用 `user_approval` 权限，并在包内定义独立审批指纹；除 `full_access` 外必须进入统一审批流程。daemon 完成 helper 签名、安装路径和 macOS TCC 权限引导前，不在默认 Registry 中启用。

基础工具在 run 开始时固定。Skill Registry 将名称、description 和 scope 作为精简目录注入 System Prompt，由模型根据用户意图进行语义选择，确定需要后再调用 `load_skill` 读取完整正文。Skill 的实际加载由对应工具调用事件审计。

### Tool 并发与重复调用

- `pi-agent-core` 使用 `parallel` 执行模式；`read_file`、`view_image`、`read_document`、`view_pdf_page`、`list_files`、`search_text`、`web_search`、`web_fetch` 标记为可并行。
- `edit_file`、`write_file`、`run_command` 标记为 `sequential`；同一批次出现任一串行工具时，整批串行。
- Tool Execution Guard 使用共享并发上限防止资源耗尽，并继承 run 的 `AbortSignal`。
- 每次调用都有超时和输出上限；Tool Execution Guard 触发中止并返回稳定错误码 `TOOL_TIMEOUT`，命令进程生命周期由实际执行器负责。
- `(sessionId, runId, toolCallId)` 作为执行幂等键；当前阶段对已获准的同一副作用 tool call 直接阻止再次执行，后续需要透明重试时再缓存并重放结果。
- 同一 run 内对“工具名 + 规范化参数 + workspace 版本”生成指纹。无上下文变化的重复调用进入循环检测：只读工具可复用当次结果，写入/Shell 工具必须阻止或重新请求审批。
- 不限制同一 workspace 的跨 session 并发。副作用工具发现目标在审批后发生变化时阻止本次调用，由 Agent 重新读取后重新修改和审批。

Tool 候选缩减只降低无关工具被选中的概率；超时、幂等和循环检测必须由执行层保证。

### Skill

Skill 是可选的上下文与操作指导，不等于工具执行权限。Skill Registry 位于 `packages/tools/src/skill-registry.ts`，具体 Skill 工具位于 `packages/tools/src/skills`；Policy 负责判断当前 session 是否可用。Skill 引用的工具仍必须通过 Tool Policy。实验性 `allowed-tools` 由用户审批后成为当前 Run 的预授权，不能由 Skill 文件自行提升权限。

Skill 来源分为三级：

- 系统 Skill 由 `packages/tools/src/skills/<skill-id>.ts` 内置并只读，当前只包含 `skill-creator` 和 `skill-installer`；与 Skill 工具共用一个目录，不建立第二套 Skill 目录。
- 全局 Skill 包含 daemon 数据目录 `skills/` 下的独立 Skill，以及用户安装插件后动态注册的插件 Skill；默认数据目录是 `~/.pi-harness/skills`，dev 使用仓库 `.pi-harness/skills`。插件注册状态保存在 SQLite，不写入系统 Skill 清单。
- 项目 Skill 按 `.agents/skills`、`.claude/skills` 顺序发现；全局独立 Skill 按 daemon 数据目录 `skills/`、`~/.agents/skills`、`~/.claude/skills` 顺序发现。同 scope 按此顺序优先，项目定义覆盖全局定义。停用优先定义后不回退到同名低优先级定义。新建和安装仍写入原有项目或 daemon 全局目录。

独立全局 Skill 和项目 Skill 以 Skill 名称命名目录并包含 `SKILL.md`。其 YAML frontmatter 必须包含 `name` 和 `description`，目录名与 `name` 一致；统一使用 Agent Skills 格式解析器，接受 `name`、`description`、`license`、`compatibility`、`allowed-tools`、`metadata` 和项目扩展 `type`。`compatibility` 为 1–500 字符，`metadata` 为字符串键值映射，标准 `allowed-tools` 为字符串，同时保留本项目已有字符串数组写法。`type` 只允许 `none` 或 `oauth`，缺省按 `none` 处理。可选资源使用 `agents/`、`scripts/`、`references/`、`assets/` 或 Skill 明确引用的其他文件，加载时仍需执行真实路径和大小检查。插件 Skill 由所属插件目录加载，安装后以全局 scope 注册并保留真实资源目录；与独立 Skill 使用相同解析器和资源读取路径，不能通过独立 Skill 卸载接口删除插件内容。

`get_skill` 与 `load_skill` 保留完整 frontmatter。`load_skill` 返回正文、Skill 根目录和有界资源清单，相对脚本及资产路径以 Skill 根目录解析，传入 `run_command` 时使用绝对路径，命令 cwd 仍固定在 workspace。资源读取检查真实路径，拒绝越界符号链接；文本按 UTF-8 加载，支持的图片按模型输入能力返回 image 内容，二进制模板返回真实路径和大小，由经审批的 Shell 直接处理或复制，不能解码成伪文本。SKILL.md 上限 128 KiB，资源上限 1 MiB，资源清单最多 200 项、扫描最多 2000 项，截断显式标记，读取支持中止。

`load_skill({ approveTools: true })` 申请 Skill 声明工具的当前 Run 预授权，普通正文及资源读取不需要授权。审批显示 Skill ID、声明和后果；`full_access` 可自动批准，其他模式请求用户确认。支持实际工具名、Read/Write/Edit/Glob/Grep/WebFetch/WebSearch/Bash 别名及 `Bash(git:*)` 等简单命令前缀；未知参数选择器不授权，复杂 Shell 表达式不能命中前缀。授权仅在成功加载后生效，新 Run 清空；每次使用前重新核对 Skill 内容指纹和启用状态，变更后失效。预授权仍需经过路径、计划模式、重复调用、超时和中止检查。

Runtime 在每次 Run 前有界读取 workspace 根目录的 `AGENTS.md`，发现系统、全局和项目 Skill，并只将名称、description 和 scope 注入 System Prompt。系统 Skill 名称保留，其他同名 Skill 由项目定义优先于全局定义。Agent 根据用户意图进行语义选择，不在 Runtime 中做关键词预加载；确定使用后通过以下内置工具渐进加载：

```text
find_skill  get_skill  load_skill  skill_creator
```

消息输入器的“+ → Skills”通过 Workspace Skill 目录接口展示只读系统 Skill，以及当前可用的全局和项目 Skill，并标注各自 scope。选中后在编辑器中保持标签展示，提交时序列化为 `$skill-name`，由 Runtime 在新消息、转向、排队追加及编辑重发时直接查找并注入正文，保持原始展示文本，同条消息重复引用只注入一次；显式加载不隐含工具预授权。成功加载的当前 Run Skill 指令不按普通工具输出截断，checkpoint 压缩保留各 Skill 最新一次加载的指令。

设置的技能页只展示系统 Skill、独立全局 Skill 和项目 Skill；动态注册的插件 Skill 统一在插件市场中查看和管理。技能页通过“新增技能”菜单区分创建与安装。创建关闭设置，在移动端同时收起侧边栏，并切换到目标 Workspace 的新会话，在输入器中插入只读系统 `Skill Creator` 标签和待补充的需求文案。安装不进入输入器，而是打开紧凑的 HeroUI 表单弹窗，只收集 GitHub 地址和可选 Skill 名称，并固定安装到全局技能目录。daemon 不接收任意 Shell 文本，只以参数数组运行固定版本的 `pnpm dlx skills add`，在临时目录下载并校验 Skill，再复制到经过真实路径检查的全局 Skill 根目录；同名目标拒绝覆盖，操作支持请求中止、超时、输出上限和失败清理。

当前已实现的插件市场只聚合 Skill 集合；MCP Client + Host 作为独立的后续能力按 [MCP 实施台账](./mcp-client-host-plan.md) 推进，不将现有 Skill 插件视为 MCP Server，也不因安装 Skill 自动启动 MCP 服务或授予工具权限。每个可用插件以 `packages/tools/src/plugins/<plugin-id>` 作为单一来源，目录内统一包含声明插件展示元数据、API 基址、OAuth 端点、OAuth 客户端凭据和 Skill 清单的 `manifest.yaml`、说明用途与来源的 `README.md`、可选的 `logo.svg`、可选的 Skill SVG，以及 `skills/<skill-id>/SKILL.md`。插件和 Skill 的目录名是稳定技术 ID；`manifest.yaml` 的 `displayName` 保存可使用中文、空格或中英混排的展示名称，`SKILL.md` frontmatter 的 `name` 必须与 `<skill-id>` 目录名一致并使用小写英文、数字和短横线。Skill 可在 `manifest.yaml` 使用 `icon` 引用插件目录内的 SVG。插件市场 API 中的子 Skill ID 直接使用 `<skill-id>` 目录名，带插件命名空间的 ID 只用于 Agent 运行时注册，并兼容读取旧版 `system:<skill-id>` 状态。daemon 从目录加载插件市场目录、Logo、Skill 图标和子 Skill，并连同安装状态与子 Skill 开关返回 Web；子 Skill 优先使用自身图标，未配置时回退插件 Logo，插件也未提供 Logo 时统一使用通用 Skill 图标。Workspace 技能目录 API 返回同样解析后的图标，消息输入器的桌面与移动端技能菜单、斜杠菜单以及 Tiptap 技能标签统一使用该图标；编辑器从当前技能目录解析标签图标，使恢复的草稿也保持一致，图标不写入发送给模型的正文。用户安装插件时写入全局安装记录，Skill Registry 在每次发现或加载时读取当前记录，把已安装且已启用的插件 Skill 动态注册为全局 Skill；插件从不并入系统 Skill 清单。集合详情中的子 Skill 复用技能页列表项，点击后按需读取正文并进入相同的技能详情布局，通用详情组件接收可选图标。关闭项不会进入 Agent 可用 Skill 目录，也不能被 `load_skill` 加载。插件列表和详情标题操作区提供统一启停开关与卸载按钮；插件开关按子 Skill 当前状态汇总，只要任一子 Skill 开启就显示开启，切换时通过现有子 Skill API 顺序统一设置，成功或失败后重新读取集合与技能目录。详情在主内容顶部独立展示 OAuth 授权区。Web 根据集合 `type` 决定是否展示授权区，不硬编码认证 Provider。卸载会同时移除集合授权、全局注册和子 Skill 开关状态。内置目录包含 Vercel、GitHub、Google、Notion 和 Supabase；Google、Notion 与 Supabase 连接各自的真实 HTTPS API 与 OAuth 服务，OAuth 客户端凭据从各自 `manifest.yaml` 的 `oauth.clientId` 和 `oauth.clientSecret` 读取，缺失时连接返回明确错误；Vercel 与 GitHub 保持现有配置。所有 Agent 请求统一经过 daemon 的按插件只读路径白名单网关；`PI_HARNESS_SKILL_GATEWAY_URL` 仅在回调地址不同于 daemon 默认地址时覆盖。

文档类插件（Documents、PDF、Presentations、Spreadsheets）在各自 Skill 目录内提供按需读取的操作参考与本地 Python 脚本，覆盖 Word 页面渲染、PDF 表单结构与外观检查、幻灯片包结构检查和表格公式缓存校验。执行前探测现有 Python、所需库和 LibreOffice/Poppler；缺少依赖时明确处理，不假定存在 Codex 专用接口。生成与编辑遵循保留源文件、写入 Workspace、实际重算或渲染、逐页或逐表检查的流程，仍使用现有工具与审批策略，不新增文档执行服务。 Word 高级操作包括明确选择的修订处理、批注、脚注尾注、书签与字段、内容控件和元数据清理，提供 OOXML 审计与渲染差异检查；PPT 提供模板部件对比和独立表格值校验；Excel 提供公式及对象清单检查；PDF 提供选页合并、选择字段填充、孤立字段修复和区域脱敏。各插件提供隔离 Python 环境的依赖清单；格式引擎不支持的 XFA、复杂 Office 原生特性由工作流明确转交可用的原生应用，不能宣称静态渲染已验证这些能力。

Supabase 插件包含开发与排障以及 Postgres 最佳实践两个 Skill。开发指南适配现有只读 Gateway 和独立配置的本地 CLI，Postgres 规则按八类存放于 Skill 的 `references/` 并按需加载；同步资源保留 MIT 许可。迁移和 SQL 操作仍需可用 CLI 及现有审批，插件内容不扩展 Gateway 写权限。

Notion 插件提供知识整理、会议准备、研究文档和需求转实施四个工作流 Skill，按需读取模板和参考资料。各工作流复用只读 Gateway 读取共享页面，产出本地可审阅草稿；当前搜索和数据源查询的分页、过滤及写入限制在访问指南中明确说明，不将本地草稿表述为已发布页面。同步资源保留 Notion Labs 许可声明。

GitHub 插件包含综合分流、审查意见处理、Actions 修复和显式请求的提交/草稿 PR 四个工作流；线程状态与失败日志使用独立认证的 `gh` 辅助脚本读取，脚本要求明确仓库和 PR，不隐式执行 Git 仓库发现。Vercel 插件包含 54 个生态 Skill，以简短 `SKILL.md`、按需读取的 `guide.md` 和配套资源承载详细内容，保留 Apache-2.0 许可及来源声明。两个插件的 Gateway 均保持只读，CLI 的安装认证、Git、dev/build、发布与生产变更遵循当前用户授权和 Workspace 规范。

Google 插件包含 Drive 文件工作流、评论审阅、Docs、Sheets 和 Slides 共五个 Skill；网关支持 Drive 文件元数据、受支持的文本导出、评论及回复读取，以及日历事件查询。文本导出不能完整反映原生文档标签页、格式、公式或幻灯片布局，涉及这些内容时需要用户提供结构化文件或可用的原生操作入口，再交由本地文档 Skill 处理。Google 在 manifest 中显式声明本地 OAuth 回调地址，凭据仍由用户配置；当前只读权限下的文档修改建议为本地草稿，不表示已写入云端。

插件特有的网关路径白名单、禁止查询值、固定请求头、OAuth 授权参数、PKCE 开关和 token 交换方式统一声明在该插件的 `manifest.yaml`，加载时完成结构、正则和保留字段校验。 可选 `oauth.callbackUrl` 为插件单独声明回调地址，授权请求和 token 交换共同使用；未配置时按 `PI_HARNESS_SKILL_GATEWAY_URL` 和插件 ID 生成。显式回调仅接受 HTTP(S) 回环地址（`127.0.0.1`、`localhost` 或 `[::1]`），不得包含凭据、查询参数或 fragment；daemon 将其 Host 纳入本机请求白名单。配置值必须与服务商登记的回调完全一致。daemon 的 `SkillConnectionService` 只编排安装与连接，OAuth 状态与 token 刷新由 `SkillOAuthService` 负责，网关请求由独立网关模块负责，不得按插件 ID 增加条件分支。

插件 OAuth 的 state 和 PKCE verifier 只存在于 daemon 内存；client secret 从插件 `manifest.yaml` 读取，不得通过 API、日志、Web 或 Skill 正文对外暴露。已写入真实凭据的插件目录必须作为私有配置管理，不得发布或共享。授权成功后 access token、可选 refresh token 和过期时间写入独立的用户私有 `skill-credentials.json`，不进入 SQLite、Session JSONL、日志、Web 或 Skill 文本。Gateway 在 access token 即将过期时串行刷新并保存 Provider 返回的新 token；插件 API 基址变化后，旧凭据不再视为已连接。插件 Skill 正文只引用配置后的 PI Harness Gateway URL；Agent 通过 `web_fetch` 访问该 URL，Runtime 附加进程内随机令牌，Gateway 验证后再按插件校验只读 API 路径并注入 OAuth token。浏览器无法取得 Gateway 令牌或上游 token。

插件 OAuth 始终在由用户操作为当前授权创建的独立小窗口中完成，不复用其他插件或上一次授权留下的窗口。点击授权时直接打开 Web 的 `/skill-oauth/:collectionId/launch` 启动页，该页只请求 daemon 创建授权地址，不直接访问 OAuth 服务商或处理凭据。daemon 完成 `/api/skill-connections/:collectionId/oauth/callback` 后重定向到 Web 的 `/skill-oauth/result` 结果页。两个 Web 页面统一使用 HeroUI 展示加载、成功或失败状态；结果页保留手动关闭操作，不自动关闭窗口。Web 在等待授权期间轮询 daemon 的脱敏连接状态，成功后立即更新插件详情，不依赖窗口焦点或页面刷新。

`skill_creator` 只创建新的最小合法 Skill，不覆盖已有目录，并复用通用文件写入权限：项目 Skill 按 workspace 写入策略处理，全局 Skill 作为 workspace 外写入在 `full_access` 下自动放行，其他策略请求审批。全局 Skill 目录属于 daemon 受保护数据，普通文件工具不能绕过路径策略修改。

### 权限和执行

```text
工具参数校验
→ Policy 返回 allow / ask / deny
→ ask 时等待用户审批
→ Sandbox 再次校验边界和资源限制
→ Tool 执行
→ 审计与 HarnessEvent
```

`app_settings` 保存一份全局审批策略，设置页和消息输入器共享该配置，所有 Session 在启动 Run 时读取当前值：

- `request_approval`：工作区文件写入和 Shell 命令逐次请求批准。
- `auto_approve`：工作区文件写入自动允许；Shell 命令视为风险操作并继续请求批准。
- `full_access`：工作区文件写入和 Shell 命令自动允许。

`run_command` 可为安全、非破坏的单条命令建议一个有序 argv `prefixRule`。Policy 只在候选规则是当前命令的精确 token 前缀、范围不过宽且不属于 Shell、解释器、`rm` 或危险 Git 子命令时，把“允许类似命令”提供给 Web。用户选择后，daemon 将该前缀追加到全局数据目录的 `allowed-command-prefixes.json`；Policy 每次判断前都重新读取该文件，手动修改或删除会立即生效。后续 Session 中只有完整命令继续以相同 token 前缀开头时才自动放行。包含管道、连接符、重定向、引用、变量或命令展开、通配符等复杂 Shell 语法的命令不保存规则，继续逐次审批。

审批卡使用 HeroUI `ButtonGroup` 展示“允许一次”和下拉入口；下拉菜单同时提供一次性批准与“允许类似命令”，只显示操作名称，不展示将保存的 argv 前缀。Web 只提交选择结果，不得提交、替换或扩大候选规则。

审批策略只决定 Policy 是否进入人工等待，不取消 workspace 真实路径、受保护目录、固定 cwd、环境变量白名单、超时、输出限制和 `AbortSignal`。因此 `full_access` 不等于绕过 daemon 的安全边界。

每个 session 绑定不可变的 `workspaceRoot`。路径在审批前和执行前都必须规范化并校验真实路径，拒绝符号链接越界。`run_command` 必须固定 cwd、超时、输出上限和中止信号，不允许不可追踪的后台进程。命令执行前后对工作区内可安全读取的小型文本文件做有界快照比较，为新增、修改和删除生成 `file.changed`；忽略受保护路径、依赖目录、内部数据目录、二进制和超大文件，达到文件数或内容容量上限时明确标记统计可能不完整。Diff 直接使用快照中的 before/after 生成，不依赖 Git 状态。快照准备、命令执行和变更统计阶段通过 `tool.updated` 实时通知 Web，命令输出按有界频率增量发送；停止 Run 必须中止当前阶段和命令进程。

撤销或重新应用某个 Run 的文件变更同样基于 `file.changed` 的 before/after 快照，不依赖 Git。执行前必须确认 Session 空闲、路径仍位于对应 workspace、所有目标文件仍与预期内容一致；任一目标冲突时整体拒绝，写入中途失败时恢复已经处理的文件。成功后追加带操作标记的 `file.changed` 事件，使 JSONL 继续作为文件变化及其应用状态的事实来源。

Sandbox 分两级：

- `guarded`：当前阶段的 workspace 真实路径、cwd、环境变量白名单、超时和输出限制。
- `isolated`：执行不可信命令时的 OS/容器隔离，只挂载必要目录，网络默认拒绝并由 Policy 显式放行；沙箱执行器统一管理命令及其子进程的生命周期。

`guarded` 不得宣称为完整安全隔离。Sandbox 每次执行返回包含限制级别、目标、耗时、退出状态和资源使用的脱敏回执，供审计和 Trace 使用。

### 动态选择

Tool 候选缩减或未来为大规模 Skill 目录增加的召回层只能减少当前暴露给模型的候选集，不能授权：

```text
用户请求 → 模型选择 Tool/Skill → Agent 调用 → Policy 独立鉴权
```

动态加载还必须校验 schema、唯一 ID、版本和来源信任。

## 7. Human-in-the-loop

Human-in-the-loop（HITL）是 daemon 的统一等待与恢复机制，覆盖：

- 写文件、运行命令等副作用工具的审批。
- Agent 需要用户补充信息或做出选择。
- Planner 在执行高风险或不可逆步骤前请求复核。
- 用户或策略配置的人工检查点。

```ts
const HumanInteractionKind = {
  TOOL_APPROVAL: "tool_approval",
  QUESTION: "question",
  PLAN_REVIEW: "plan_review",
  CHECKPOINT: "checkpoint",
} as const;

type HumanInteractionKind =
  (typeof HumanInteractionKind)[keyof typeof HumanInteractionKind];

interface HumanInteractionRequest {
  id: string;
  sessionId: string;
  runId: string;
  kind: HumanInteractionKind;
  prompt: string;
  options?: string[];
  toolCallId?: string;
  createdAt: number;
  expiresAt: number;
}
```

显式 Plan 模式通过 `RunUserInput.mode` 从 Web 传入 daemon，输入规范化必须保留该字段，供 runtime 注入 Plan 提示词并启用确认前的副作用限制。用户消息将 `mode` 作为元数据保存在 Session JSONL，Web 按该元数据回显 Plan 标签，编辑重发继承原消息模式。

工具审批由 `beforeToolCall` 触发；Agent 主动提问通过专用 `request_user_input` 工具触发。两者共用 daemon 内的 `HumanInteractionService`，但安全审批仍由 Policy 作出决策。

`request_user_input` 提交非空问题列表，每题包含唯一非空 ID、标题、正文与选项列表；不以题目数量、选项数量或展示文本长度拒绝可渲染的请求，选项说明可省略。选项数量不是固定值：模型只提供完成当前决策所需的最少选项，通常为 2–3 个；纯文本问题可使用空选项列表。模型按决策是否互斥决定每题的 `multiSelect`，省略或为 `false` 时单选，为 `true` 时多选。推荐项排在第一位。模型通过每题的 `allowCustomInput` 决定是否显示“自己输入”，为 `false` 时隐藏并由 daemon 拒绝自由输入回答；省略时默认显示。关闭自由输入的普通问题必须有选项。普通问题使用 `question`，在消息输入器位置显示分页交互卡片；单选回答保存 `selectedOption`，多选回答保存 `selectedOptions`，两者互斥，均保存最终 `value` 文本，daemon 按请求校验选择模式与选项。问题按页展示，单选后自动前进，多选保留当前页以便继续勾选，非最后一页的主按钮显示“下一页”，仅要求当前题已作答，点击后保留答案并前进；最后一页显示“提交回答”，要求全部问题已作答；前后翻页按方向滑动，减少动态效果时即时切换。卡片头部和底部操作保持固定，中间问题内容区使用视口约束的最大高度，超出后在 HeroUI `ScrollShadow` 内纵向滚动。

计划模式的确认使用 `plan_review`，请求必须携带完整的 `planMarkdown` 和唯一确认题。Web 在 `request_user_input` 调用参数生成期间即把 `planMarkdown` 增量投影为对话时间线中的只读 Markdown 消息，并在正式请求到达后切换为完整版本；计划书默认限制摘要高度，超出时通过 HeroUI `ScrollShadow` 纵向滚动，并提供展开全文与收起操作。消息输入器区域沿用用户输入卡片的层级与宽度，只展示两个尺寸、间距、椭圆轮廓和尾部操作一致的互斥选项：“是，实施此计划”和“否，并告诉 AI 应该如何做得不同”。两种选择都转换为普通用户消息，写入时间线并通过 steering 队列进入正在等待的同一个 Agent Loop，不调用 `abort()`，其中第一项是立即开始执行的指令；第二项接收自然语言修改意见，由 Agent 生成下一版完整计划书，用户不直接编辑 Markdown。每次请求、修改与确认都以 `input.requested` / `input.resolved` 追加到 Session JSONL，对应选择同时通过普通 `message.completed` 保存，因此本地文件保留完整版本链并可在重启后恢复，无需在确认前额外写入 workspace。`request_user_input` 不作为普通工具卡片展示，等待回答时不显示“正在思考”。完整调用参数与失败详情仍保留在 Trace 和 Session JSONL。

流程：

```text
产生请求
→ 先追加 requested 事件
→ SSE 通知 Web
→ run 进入 awaiting_input
→ 用户回复 / 拒绝 / 超时 / abort
→ 先追加结果事件
→ 恢复 Agent 或终止当前操作
```

约束：

- 等待必须支持超时、Agent abort 和 daemon 关闭，不持有数据库事务。
- Run 状态按 `running → awaiting_input → running | aborted | failed` 转换，不把人工等待记为模型失败。
- 等待中的 run 仍是活动 run；一个 session 不得同时启动新 run。
- 审批只能解决已持久化的规范化请求，Web 不得在回复时替换工具参数或命令前缀规则。
- 解决请求时校验 session、run、interaction ID 和当前状态，重复回复返回冲突。
- SSE 重连后必须从 session 快照或 JSONL 恢复待处理请求。
- daemon 重启时无法恢复原进程中的 Agent 调用栈；启动恢复必须把未终结审批记为 `expired`，并把对应 run 记为 `aborted`，避免遗留不可解决的等待状态。
- 恢复执行前再次运行 Policy 和 Sandbox 校验，防止等待期间 workspace 发生变化。
- 普通问答默认只进入 Session JSONL，不自动写入长期 Memory。

计划模式是一次顶层 Run 的模式，不创建独立 Agent。Web 通过添加菜单在编辑器内插入 Plan 标签，复用 Skill 标签样式并使用独立主题色；删除标签取消本次消息的计划模式，发送时从标签派生模式，标签本身不进入正文，并在发送成功后随草稿清除。Runtime 为该 Run 追加计划模式指令，并在用户确认前只允许读取上下文和进行人工交互；写文件、Skill 写入和 Shell 等副作用即使策略允许也会被 Runtime 阻止。

Agent 先读取上下文；目标、范围或约束不足时使用普通的 `request_user_input(question)` 补充信息，一次请求可以包含一个或多个相关问题，并继续复用现有分页逐题回答流程；进入澄清时 Web 根据既有 `run.started` 与 `input.*` 事件在消息链展示“正在询问问题 / 正在等待你的回答”，并随回答或超时更新状态。收到回答后重新判断，必要时可以连续多轮提问。条件充分后持续思考并使用 `request_user_input(plan_review)` 提交一份独立、完整、可直接阅读的 Markdown 计划书，内容至少覆盖目标、现状、实施方案、影响范围、风险与验证方式。用户给出自然语言修改意见时，Agent 重新判断其中是否存在会实质改变新版计划的歧义或缺失决策：存在时继续复用普通问题流程做最少量澄清，否则用最佳判断与只读检查解决次要取舍，直接生成新的完整版本并再次等待确认；收到 `confirm_plan` 后不再发起任何用户输入，立即解除副作用限制并执行。Runtime 不接受未确认的计划模式 Run 以普通 assistant 结束：续轮应根据仍缺失的实质信息进入提问，否则生成首版或修订后的 `plan_review`；确认后若模型只返回确认或稍后继续的短话术，Runtime 同样不发出成功终态，而是在当前 Run 内有界续轮并要求立即执行或报告具体结果；超过有界重试次数后分别以 `PLAN_REVIEW_REQUIRED` 或 `PLAN_EXECUTION_STALLED` 明确失败，不能产生虚假的成功终态。普通模式继续保留由 Agent 按任务需要调用 Planner/Todos 的隐式规划行为。

Web 至少提供“获取当前待处理交互”和“一次性解决交互”的 API。危险操作必须显示规范化目标、参数摘要和后果，拒绝、超时和取消都必须有明确状态。

## 8. Context、Planner、Memory 与 RAG

### Context Pipeline

Context 按职责分为三层，避免把“完整历史”“当前任务状态”和“本次模型输入”混成一份不断膨胀的文本：

| 层级 | 内容 | 事实来源与生命周期 |
|---|---|---|
| Session 事实层 | 完整用户/Assistant 消息、Tool 调用与结果、审批、文件变化、Markdown 计划书及其版本、Plan、Todos | Session JSONL；只追加，不因压缩覆盖或删除 |
| 工作状态层 | 当前目标、明确约束、关键决策、已完成事项、未完成事项、阻塞与下一步 | 最新 `context.compacted`、`plan.updated`、`todo.updated` 和待处理交互事件；从 JSONL 重建，checkpoint 内容在下次压缩前保持不变 |
| 热上下文层 | System Prompt、Tool 定义、工作状态、当前 Run 的任务契约和最近完整消息组 | 每次模型请求前由 Runtime 完整投影；`run.started` 仅在 Session 首次或内容变化时为 Trace 保存 System Prompt、Tool 定义与来源 Context 快照，其余请求上下文正文不重复持久化 |

`context.compacted` 随 Session 写入 JSONL，但它是可重建的派生 checkpoint，不替代原始消息。可读 Markdown 只可作为调试或导出视图，不作为 Runtime 事实来源，也不自动写入用户 workspace。

```text
System Prompt（含 workspace 约束 / AGENTS.md / Skills / Memory）
+ Tool 定义
+ 最新稳定工作状态 checkpoint
+ 当前 Run 的原始任务契约
+ 最近 Session 消息序列（含用户文本、附件和 `@` 引用；user → assistant / tool call → tool result → assistant ...）
```

每次请求先根据模型 `contextWindow` 扣除输出预留和安全余量，再对热上下文执行以下固定顺序：

1. 每条历史附件或引用使用独立固定预算，新增消息不得重新分配并改写更早前缀；超过 8192 字符的 Tool 文本结果从首次投影起固定保留 4096 字符头部与 1024 字符尾部。完整内容仍留在 JSONL，需要时重新读取来源。
2. 把消息按完整原子组处理；Assistant tool call 与其 tool result 不得拆开。
3. 始终保留当前 Run 的原始用户请求、最近完整消息组、Plan/Todos 对应的原始 Tool Result 和待处理 HITL；不得在每次请求前把可变工作状态改写进 checkpoint 头部。
4. 热上下文达到可用输入预算的 80% 时，将旧消息组与上一 checkpoint 生成新的完整结构化工作状态，并保留约 16% 窗口的逐字尾部。摘要请求逐字重放当前主请求的 System Prompt、Tool schemas 和待压缩消息前缀，只把压缩指令追加在尾部，以复用 Provider 热缓存。后续压缩只处理“上一 checkpoint + 新增历史”，不重复摘要完整 Session。新 checkpoint 是完整替换，必须应用较新的用户纠正并移除已被替代的决策或约束。
5. 开始压缩时先追加 `context.compaction_started`，完成后追加 `context.compacted`，再使用新 checkpoint 继续模型请求；Web 将两者合并为思考链中的同一条进行中/完成状态，原始消息仍完整留在 JSONL。
6. 压缩后仍超出窗口时返回稳定的 `CONTEXT_WINDOW_EXCEEDED`，不依赖 Provider 静默丢弃最早消息。

结构化 checkpoint 至少包含：

```ts
interface ContextCheckpoint {
  objective: string;
  constraints: string[];
  decisions: string[];
  completed: string[];
  pending: string[];
  blockers: string[];
  nextAction: string;
}

interface ContextCompactedData {
  checkpoint: ContextCheckpoint;
  compactionId?: string;
  previousCompactionId?: string;
  compactionReason?: "threshold" | "milestone";
  compactionStrategy?: "model" | "fallback";
  coveredMessageRange?: { start: number; end: number };
  sourceMessageCount: number;
  compactedMessageCount: number;
  beforeTokens: number;
  afterTokens: number;
  compactionUsage?: Usage;
}
```

`sourceMessageCount` 表示 checkpoint 生成时的消息投影边界；普通压缩下，它等于 checkpoint 已覆盖的完整原始消息前缀长度。恢复历史 checkpoint 后，Runtime 以恢复事件发生时的消息数量作为新的热上下文尾部起点：原始消息继续保留用于界面展示、审计和显式历史检索，但被回退的后续分支不再自动进入模型请求。压缩模型输出必须按固定结构验证；失败时保留上一 checkpoint，并使用确定性裁剪安全降级，不能让压缩失败伪装成主任务成功。

每个 checkpoint 同时记录稳定版本 ID、上一版本 ID、覆盖的消息范围、触发原因和生成策略。`context.checkpoint_restored` 记录当前工作 checkpoint 的目标事件引用；Runtime 按事件顺序重放时同时重建恢复边界，不修改或删除原始消息。Web 可列出任意两个版本并排对比，在 Session 空闲时恢复所选版本。新的顶层 Run 是确定性的任务边界：首次投影前，Runtime 自动清空上一 Run 的 Plan/Todos 并追加 `context.working_state_reset`；活动 Run 内的 follow-up 继续复用工作状态，只有 follow-up 中途替换任务时才保留显式 `reset_working_state`。Session 事实始终完整保留。

Provider Adapter 原生支持 loss-aware compaction 时优先保存并继续传递 Provider 返回的 opaque 状态；Provider 未提供该能力时，由 Runtime 生成上述可移植 checkpoint。Opaque 状态只用于对应 Provider 的后续请求，不能解析成业务字段，也不能替代可审计的结构化工作状态。

长任务每次压缩后都重新注入当前任务契约和稳定 checkpoint；显式 Plan 已确认时，最终 Markdown 计划书作为用户级任务契约在之后每次上下文投影中重新注入，不能被压缩丢失。压缩模型同时读取最新 Plan/Todos，未被压缩的工作状态继续来自原始 Tool Result。继续修改前通过工具重新读取相关 workspace 文件。上下文管理降低跑偏概率，但不宣称模型永不偏离；验收以可恢复、可追溯、关键约束持续注入和副作用前重新校验为准。

### 用量统计

每条 assistant `message.completed.data` 中的 `usage` 是 Provider 实际用量的事实来源；发送前的 Context 分类只能估算，并通过独立快照记录。Web 从 Session 快照和 SSE 事件派生展示数据，不建立 SQLite 用量副本：

- 单次 Run 按 `runId` 汇总其中所有 assistant 请求；一个 Run 可能因 Tool Call 或自动续轮包含多次模型请求。
- Session 累计分别汇总 input、output、cache read、cache write、reasoning、total tokens 和 PI 模型价格表计算的预估费用。
- `reasoning` 是 `output` 的子集，只单列展示，不重复计入 Token 合计。
- 每次调用 `streamFn` 前追加 `context.usage_snapshot`，统计该次请求实际携带的完整活动 Session Context：System Prompt、按来源分开的 Run Context、Tool 定义和按顺序累积的消息（含 tool call/result）。模型请求仍在每次调用时携带完整 System Prompt、Tool 定义与来源 Context。`run.started.contexts` 使用 `{ type, label, content }[]`：Session 首次记录全部来源，后续按 `type` 独立比较，只保存新增或内容变化的条目；`removedContextTypes` 记录被移除的来源。当前来源包含 `AGENTS.md` 与 `Available Skills`，新增来源继续追加独立条目，不并入已有类型。System Prompt 与 Tool 定义作为一组快照，仅在首次或任一内容变化时保存。用量快照只持久化分类 Token 估算值及请求序号，原始消息继续以 Session JSONL 为唯一事实来源，不按请求重复保存 Context 原文。
- 当前上下文总量优先使用同一次 assistant 响应的 `input + cacheRead + cacheWrite` 校准，响应尚未返回或 Provider 未报告用量时使用快照估算值，再除以当前 Session 模型的 `contextWindow`。失败或中止请求仍保留其发送前快照，已报告的部分用量同时计入累计。
- Web 取最新一条完整 Session Context 快照表示当前窗口占用；分类值不跨模型请求累加，避免把多次携带重叠历史的输入反复计入当前窗口。Run 与 Session 累计另外按 Provider 报告的请求用量汇总。
- Provider 未提供用量、订阅模型没有可映射账单或自定义模型费率为零时，金额显示为未提供，不宣称等同于供应商账单或套餐余额。
- 上下文压缩使用同一 Provider 的独立模型调用，其 `compactionUsage` 计入对应 Run 与 Session 的请求数、Token 和费用；该调用重放主请求可缓存前缀，只在末尾追加压缩指令，不会用于校准主任务当前 Context。
- 主任务和压缩请求均传递稳定 `sessionId` 与 `cacheRetention: "long"`，并保持 System Prompt、Tool schemas、checkpoint 与历史消息顺序确定；不支持该能力的 Provider 可以忽略，支持的 Provider 复用 prompt cache。
- Trace 的 Request 详情只描述对应的 Assistant 模型请求。其“Session cumulative”只累计到当前 Request 为止的 Assistant 消息用量，不混入工具、审批或上下文压缩调用；Trace 只在 `run.started` 首次携带或内容变化时生成 System/Context 记录，未变化的新 Run 不重复展示。完整会话累计仍由上下文与用量入口按上述口径展示。TTFT、生成耗时和吞吐量分别由同一次请求的 `context.usage_snapshot`、Assistant `message.started` 与 `message.completed` 时间推导。

### Planner

第一版 Planner 是 `packages/tools/src/tools/planner.ts` 提供的控制工具，由同一个 Agent 调用并更新当前 run 的执行步骤状态，不创建独立 Agent。工具通过回调产生 `plan.updated` 事件，不直接写入 JSONL、数据库或 SSE。它服务于执行过程的进度展示，与显式 Plan 模式中需要用户确认的 Markdown 计划书是两类状态。

Web 只重建活动 Run 的最新 Plan，并使用 assistant-ui `AgentPlan` 在消息输入器上方的可折叠工作状态区左栏原位更新；标题使用 `Plans`，保留独立的完成数、总数和步骤状态，并与 Todos 分栏展示。两栏标题固定在顶部，只有下面的条目分别滚动并隐藏可见滚动条，且均不显示标题下的进度横线。折叠态使用居中的单个椭圆胶囊分别概括 Plan 与 Todo 进度，展开内容锚定胶囊向上悬浮，不参与底部区域布局；桌面端按单项或双项使用稳定的最大宽度，避免进行中描述在完成后消失时收缩，移动端 Plan 与 Todo 摘要等分可用空间。浮层与胶囊始终等宽并使用相同 surface 背景，浮层不显示边框或边缘阴影，内部间距保持紧凑一致。Run 进入终态后隐藏该区域。历史更新继续保留在 Session JSONL 和 Trace，不在思考链中重复生成计划卡片。

### Todos

Planner 描述策略、顺序和依赖；Todos 是 `packages/tools/src/tools/todos.ts` 提供的控制工具，用于维护面向用户的当前执行清单，两者不强制一一对应。

```ts
const TodoStatus = {
  PENDING: "pending",
  IN_PROGRESS: "in_progress",
  COMPLETED: "completed",
  BLOCKED: "blocked",
  CANCELLED: "cancelled",
} as const;
```

Todo 至少保存 `id`、`runId`、`content`、`status`、可选 `planStepId`、`evidence` 和更新时间。Agent 通过 `update_todos` 更新；模型不提交 `evidence` 或 `toolCallId`，Runtime 在 `completed` 项写入前自动关联当前 Session 最近成功的工具结果。没有成功工具结果时拒绝完成，不能仅依赖模型文本声明。Todo 变更使用 `todo.updated` 追加 JSONL，恢复时从事件重建，不建 SQLite todos 副本表。

Web 使用 assistant-ui `TodoList` 在同一工作状态区右栏展示活动 Run 的最新非空 Todos，并保留独立的完成数、总数、修订号和条目状态；标题固定在顶部，条目在下方独立滚动。工作状态区默认折叠为带类型图标、独立语义色且上下留白一致的单个椭圆进度摘要，展开后显示完整双栏内容；Run 完成、失败或中止后立即隐藏，不把 Plan/Todo 控制工具重复加入思考链。

### Memory

区分四类数据：

| 类型 | 作用 | 事实来源 |
|---|---|---|
| Working Memory | 当前 Agent context | Agent state |
| Session History | 完整对话与执行记录 | Session JSONL |
| Long-term Memory | 用户偏好、项目事实、经验 | 可审计的记忆记录 |
| Retrieval Index | 全文/向量检索 | 可重建派生数据 |

长期记忆必须包含 scope（user/workspace/session）、来源、时间、写入策略、去重和删除能力。不默认把所有对话写入长期记忆。

### Retrieval

检索引擎可以共用，索引必须按 namespace 隔离：

```text
tools  skills  workspace-documents  user-memory  session-memory
```

检索时先应用 user/workspace 范围过滤，再计算相似度。Retrieval Index 不是事实来源，必须可从原始数据重建。

初期 Retrieval 留在 `apps/daemon/src/memory` 或 Tool Selector 内。当 Tool/Skill 选择和 Memory 都成为真实消费者时，再提取 `packages/retrieval`。

当前 `search_session_history` 直接检索 Agent 从 Session JSONL 恢复出的完整消息，返回有界片段和原始消息序号。它用于 checkpoint 缺失旧事实时的按需取回；workspace 代码事实仍必须重新读取文件。第一版采用倒序线性扫描，不建立新的事实副本；只有万级消息检索出现可测延迟时才增加可重建索引。

## 9. HarnessEvent 与 SSE

Web 只消费稳定的项目事件：

`HarnessEventType`、`HarnessEvent` 与消息增量类型只在 `agent-runtime/harness-event` 定义一次。daemon 通过 runtime 主入口复用，Web 通过浏览器安全的 `@pi-harness/agent-runtime/harness-event` 子路径复用，不在各端维护副本。

```ts
interface HarnessEvent<T = unknown> {
  id: string;
  seq: number;
  sessionId: string;
  runId?: string;
  timestamp: number;
  type: HarnessEventType;
  data: T;
}
```

核心事件：

```text
run.started          run.completed        run.failed
run.aborted          run.awaiting_input   run.resumed
message.started      message.delta        message.completed
tool.started         tool.updated         tool.completed
tool.failed          approval.requested   approval.resolved
file.changed         plan.updated          input.requested
input.resolved       input.expired         todo.updated
context.usage_snapshot  context.compaction_started  context.compacted  context.checkpoint_restored
context.working_state_reset  message.branch_started  tool.skipped
```

同一 session 的 `seq` 必须严格递增，客户端依靠它去重、排序和重连。SSE 断开不中止 run，只有 abort API 可取消 Agent。

`approval.*` 用于工具安全决策，`input.*` 用于提问、Markdown 计划书版本、计划确认和人工检查点。`message.delta` 中的工具调用增量携带稳定的 `toolCallId` 和 `toolName`，Web 在参数生成期间即投影运行中的 ToolCall，后续由 `tool.*` 事件更新执行阶段与结果。`message.delta` 和 `tool.updated` 只用于实时 SSE，不写入 JSONL；其他影响恢复、审计或用户可见状态的事件按顺序追加。

`provider_settings` 同时保存内置 Provider 的用户设置和自定义 Provider 的非敏感定义：

```text
provider_id         TEXT PRIMARY KEY     # 内置 ID 或 custom:<uuid>
kind                TEXT NOT NULL        # builtin | custom
name                TEXT NULL            # 自定义 Provider 必填
protocol            TEXT NULL            # 自定义 Provider 必填

```

`kind`、`enabled`、认证模式和自定义必填字段由数据库约束与 service 校验共同保证；repository 读取 JSON 后再次校验模型 ID 数组。`model_ids_json` 只作为 Provider 聚合内部的一组配置保存，不单独查询。API Key、OAuth Token 和认证 Header 不得进入该表。

`workspaces` 使用 daemon 通过操作系统目录选择器取得并经 `realpath` 校验的 `root_path` 去重，并保存可编辑的 `display_name`、软移除时间 `removed_at` 与展示顺序 `sort_order`；工作区顺序由 daemon 写入本地 SQLite，不使用浏览器 `localStorage`。Web 创建 Session 时只提交 `workspace_id`，不提供或覆盖真实根目录。移除 Workspace 只隐藏引用及其 Session 列表，不删除本地文件、Session 索引或 JSONL；再次添加同一 `root_path` 时清除 `removed_at`、复用原 `workspace_id`，原会话随之恢复。`sessions` 保存 `workspace_id`、`provider_id`、`model_id`、`thinking_level`、`title`、`last_seq`、`archived_at` 和时间戳。Session 创建后不修改 `workspace_id`；模型与推理强度只影响后续新 Run；归档只更新轻量索引，不删除 Session JSONL。`app_settings` 以稳定 key/value 保存所有 Session 共用的审批策略、已允许的安全命令 argv 前缀、繁忙时 `queue | steer` 发送偏好、文件打开模式与默认应用、输出详细程度与推理摘要方式，以及新会话默认 `providerId`、`modelId` 和推理强度等 daemon 应用设置，不使用浏览器 `localStorage`。输出详细程度只覆盖支持 `text.verbosity` 的模型 API，推理摘要只覆盖支持 `reasoning.summary` 且本次已启用推理的模型 API，其他 Provider 保持原请求行为。默认应用的真实路径仅由 daemon 通过操作系统应用选择器取得并持久化，Web 只接收应用名称与可选图标。Runtime 在 System Prompt 中提供当前真实 Workspace 根路径，要求模型生成可独立解析的本地文件链接；daemon 兼容将旧消息中不存在的 `project/` 与 `/workspace/` 前缀按当前 Workspace 解析。用户主动点击本地路径时，相对路径按当前 Workspace 解析，绝对路径可位于外部；目录继续交给系统文件管理器，文件在“每次询问”模式下先由 Web 展示 HeroUI 应用选择弹窗，再由 daemon 调起系统选择器；勾选“以后始终使用此应用”后同时保存应用与“始终使用指定应用”模式。已保存应用不存在或无法打开目标文件时返回 `application-required`，由 Web 重新询问。

`sessions` 只保存轻量索引，不建立 messages、runs、tool_calls、approvals 或 file_changes 事实副本表。`session_search_documents` 与 `session_search_messages` 是可从 JSONL 重建的派生全文索引，只保存可见用户/助手文本、事件定位和源文件大小，不参与 Session 恢复。SQL 集中在 repository，表结构只通过显式 migration 修改。

会话搜索以 SQLite FTS5 trigram 派生索引查询中英文子串，JSONL 仍是完整消息的唯一事实来源。daemon 用 JSONL 文件大小和进程内追加版本识别过期 Session，只重建发生变化的索引；索引缺失或不一致时可直接从当前有效分支重建。daemon 只返回命中 Session、最近消息描述、有界命中摘要和命中的 `message.completed` 事件 ID；Web 不批量拉取完整会话内容用于本地搜索。用户选择消息命中结果后，Web 通过瞬时 UI 状态把事件 ID 与查询文本交给会话页，由虚拟列表定位消息并短暂高亮关键词，不把定位信息写入 URL。普通会话切换只获取渲染对话所需的轻量事件投影，不传输重复的 Tool Result 消息、Tool 内部详情和文件 diff；完整事件快照只在用户打开 Trace 时按需获取。Session 子路由不以快照请求作为导航提交屏障，侧栏按下态立即反馈并同步提交目标位置，冷快照继续通过 TanStack Query 展示既有加载态。普通会话快照与 SSE 使用相同轻量投影；Trace 只在打开时获取完整快照并建立独立订阅，关闭后释放完整缓存。普通会话快照短期保留以支持切换；侧栏 hover 或开始按压时预取冷会话快照，子路由复用已认证状态，桌面虚拟列表从估算末尾初始化并在首个稳定帧完成定位。

Web 将 `message.delta` 与 `tool.updated` 按 100ms 窗口批量写入 Query cache，合并同一消息内容块的 delta、只保留每个工具的最新进度；侧栏仅在非增量事件时更新。其他事件立即连同待提交增量按序刷新，订阅卸载时提交尾部增量。助手正文、思考与计划书使用 HeroUI Pro 的 `StreamMarkdown` 接收流式状态，复用稳定的块标识并关闭逐字动画，避免每次内容变化重新挂载 Markdown 块。

会话在跟随状态下，每次消息批量更新后通过虚拟列表滚到底部；用户向上滚动、编辑消息或使用轮次导航时暂停跟随，回到底部后恢复。流式内容的异步高度变化由虚拟列表的末尾锚定补偿。滚动容器关闭浏览器原生滚动锚定；虚拟列表保留同步范围更新与直接 DOM 定位，缓存取消息 key 的函数，减少滚动与悬停时的位置重算。轮次导航继续通过虚拟列表定位，并根据实际滚动位置更新当前轮次。

### 长会话渲染预算

流式代码块在 fence 闭合前使用等宽纯文本，闭合或停止后高亮；超出 20,000 字符的代码保留纯文本与完整复制能力。折叠工具卡不序列化请求和结果，图片结果仅展示元信息。历史消息投影按 Run 复用，流式更新只重投影发生变化的 Run；文件摘要按文件事件版本缓存，避免正文增量触发重复 Diff。完整审计内容仍以 daemon 的 Session JSONL 为事实来源。

普通会话的 `file.changed` 只投影路径与状态，不传输 before/after；`GET /api/sessions/:sessionId/runs/:runId/file-changes` 返回按 Run 合并的变更统计，`includeContent=true` 只供已打开的审核面板加载原文，面板卸载后立即回收该 Query。普通对话中的图片工具结果投影为 MIME 元信息，完整结果继续保存在 JSONL 和 Trace。Trace 忽略正文 delta，工具进度按 500ms 合并，完成 Run 的轨迹复用缓存。

普通会话中的工具文本结果最多携带 16,000 字符预览；展开工具后通过 `GET /api/sessions/:sessionId/events/:eventSeq` 获取原始完整结果，折叠后卸载详情并立即回收其 Query。该裁剪只作用于 Web 投影，不修改模型上下文、审批入参或持久化事件。


### Session JSONL

每个 session 对应一个 `<sessionId>.jsonl`，每行是完整 `HarnessEvent`。JSONL 是对话、run、工具、审批、人工交互、Markdown 计划书版本、执行 Plan、Todos 和文件变化的唯一事实来源。

规则：

- 同一 session 串行追加，`seq` 严格递增；由于实时事件不落盘，JSONL 中的 `seq` 允许不连续。
- `run.started.data` 每次保存该 Run 实际使用的 Provider、Model、推理档位和最大输出；System Prompt 与 Tool 定义作为同一可选快照，只在 Session 首次或任一内容变化时保存。来源 Context 按 `type` 独立保存首次、新增、更新与移除，不因同组其他来源变化而重复写入。模型请求本身仍由 Runtime 每次携带完整上下文。
- `message.completed.data` 保存完整 `AgentMessage`。
- `message.branch_started` 只改变当前有效分支，旧事件不删除；恢复时从目标用户消息开始折叠旧后缀。
- 先追加 JSONL，再更新 SQLite 索引；索引失败不删除已写入事件。
- 恢复时逐行校验。只能丢弃崩溃留下的不完整末行，中间行损坏必须报错。

## 11. Trace 与观测

Trace 从 `HarnessEvent` 和 Provider/Tool/Retrieval 边界订阅生成，初期放在 daemon，不影响 Agent 主流程。

Web Trace 以 Session 为连续观察范围，按 `seq` 展示全部 Run，不提供按 Run 切换的选择器。Trace 初始化或切换 Session 时不默认选中任何记录，详情面板保持关闭，只有用户主动选择记录或 Request 后才显示对应选中态与详情。时间轴按事件顺序划分连续等宽槽位，每个槽位只展示一条记录；泳道只表达事件类型，不表达并发，同一横向位置不得叠放多个事件。真实起止时间和耗时只在 Tooltip 与详情中展示，未实际执行的 Tool 仍保留其真实零时长语义。`run.started` 首次携带 System Prompt/Tool 定义或来源 Context 快照时生成初始记录，后续仅在对应快照变化时生成更新记录；未变化的新 Run 不重复展示，Tool 详情继续使用截至当前 Run 最近一次有效的 Tool 定义快照。`run.completed`、`run.failed` 和 `run.aborted` 使用独立 Run 记录，Chip 与时间线分别使用 success、danger 和 warning 语义色，其中失败详情明确展示真实错误信息与错误码，不归入 System Prompt。`message.branch_started`、排队 follow-up 和 steer 作为普通记录进入同一记录流。`runId` 继续用于关联具体模型、Tool、审批与错误，不把 follow-up 或 steer 拆成新的 Trace。Turn 从一条真实用户消息开始，到下一条真实用户消息之前结束，期间的模型、Tool、审批与 Context 事件归入同一 Turn；同一 Run 在用户消息前记录的来源 Context 快照归入该用户消息开启的 Turn，若该 Run 没有真实用户消息则仍作为 Turn 0 的 Session 事件。Request 按 Session 内实际模型请求顺序独立编号，不能复用 Turn 编号，并在对应 Assistant 记录的顶部边界显示独立圆点标记。圆点不属于相邻事件 item，选择圆点只打开 Request 详情，不触发事件 item 或 Turn 的选中态；`Request #N` 只在圆点 hover 或键盘聚焦时通过 Tooltip 显示。圆点之间不连接；未选中为白色外圈与 muted 灰色内芯，hover 或键盘聚焦时只把内芯改为 accent 蓝色；选中时外圈改为 accent 蓝色，内芯改为 20% 透明度的 accent 蓝色，不显示按钮容器的 hover 背景。Request 详情使用 Summary、Options、Usage 和 Timing 四个页签，字段与视觉遵循项目现有 Trace 设计；只统计对应 Assistant 模型请求，可从 Result 返回 Assistant Message 详情。Run、System、Context、User、Tool、Approval、Assistant 等记录各自使用独立详情组件和对应页签，不用统一摘要模板掩盖类型差异。User 详情使用 Summary、Preview、Raw 和 Source：Preview 渲染用户 Markdown，Raw 按原始 content block 顺序及动态类型展示纯文本，Source 展示从已验证用户消息角色投影出的 `{ kind: "user" }` 来源对象。Assistant 详情使用 Summary、Preview 和 Raw：保留 `message.completed` 中 `thinking`、`text` 与 `toolCall` 的原始顺序，Preview 对思考和正文使用 Markdown 展示并列出 Tool Call 入参，Raw 只按动态 block 类型展示纯文本；Source 的 `Request #N` 通过请求事件 ID 打开对应 Request 详情，Tool Call 通过 `toolCallId` 跳转到对应 Tool 轨迹。Tool 详情使用 Summary、Payload、Result、Schema 和 Timing：Summary 可返回发起该调用的 Assistant Message，并预览入参、结果、最近一次有效工具快照中匹配到的工具名称、描述与参数 Schema；Timing 使用 Session 生命周期事件的时间戳。Approval 详情使用 Summary、Request、Result、Timing 和 Raw：Summary 展示状态、decision、审批 ID、工具、目标、参数摘要与风险，关联到对应 Tool Call；Request 与 Result 分别保留 `approval.requested` 和 `approval.resolved` 的原始数据；Timing 展示请求、处理、截止和等待时长。审批通过只表示允许工具在执行前重新校验后继续，不表示工具已经执行成功，实际执行结果由关联 Tool 轨迹展示。顶部 Session 状态和记录总数使用稳定的中性展示，不随所选记录改变语义色。

来源 Context 按 `type` 独立比较；只有 `AGENTS.md` 变化时，只生成对应的 Context 更新记录，不得重复展示未变化的 `Available Skills`。被移除的来源使用 `removedContextTypes` 保留可审计的变化记录。

新 Run 只有在持久化真实用户消息后才开启下一个 Turn；用户消息前失败的 Run 终态保持为 Session 事件，不得复用上一轮编号。

同一 Tool 的审批等待与实际执行在时间线上必须前后相接，不得表现为并行。`tool.started` 只表示 Tool 生命周期和执行前检查开始；存在审批时，Approval 使用 `approval.requested → approval.resolved` 统计等待时长，Tool 执行区间从批准事件结束后开始统计，并在两条泳道的共同边界绘制垂直连接表示交接。拒绝、超时或仍在等待时，Tool 只保留零时长生命周期点，不生成执行区间。

至少记录：

- `traceId`（默认等于 `runId`）、`spanId`、`parentSpanId`。
- Provider、Model、首 token 时延、总耗时、token 和费用。
- Tool、审批、上下文压缩和 Retrieval 耗时。
- Tool/Skill 候选召回、实际选择、等待队列、超时、重放和重复调用阻止。
- Planner 与 Todo 状态变化，以及 Sandbox 执行级别。
- Human-in-the-loop 等待时间，与模型和工具执行耗时分开统计。
- 取消、重试和稳定错误码。

Trace 写入前必须脱敏，不记录 API Key、Authorization、Cookie、完整环境变量或敏感文件内容。当出现第二个运行时消费者或多个输出 sink 时，再提取 `packages/observability`。

## 12. 必要的运行保障

- 所有外部输入在 TypeBox schema 边界校验。
- Run、Provider、Tool、审批、Retrieval 都支持取消、超时和稳定错误码。
- Provider 层处理限流、可控重试、模型能力检查和成本预算。
- daemon 优雅关闭时停止接收新 run，中止或等待活动任务。
- daemon 只监听 `127.0.0.1`，校验 Host/Origin，状态变更请求执行同源保护。

## 13. 演进顺序

以下保留既有能力的演进说明。新增 MCP Client + Host 工作按 [完整目标与任务台账](./mcp-client-host-plan.md) 推进，具体实现进度只在该台账维护；阶段性 Tools 闭环不能代替完整能力验收。

1. 完成持久化 CredentialStore、Provider API 和用户自定义 Provider，用 daemon 数据替换 Web 的 Provider mock。
2. 接入 Agent Runtime、HarnessEvent、SSE、SQLite 索引和 Session JSONL，跑通无工具对话。
3. 完成 Tool Registry、Policy、Human-in-the-loop、Sandbox 和文件变化。
4. 完成 AGENTS.md/Skill、Tool/Skill Registry、Context 预算、输出截断和结构化 checkpoint 压缩；Provider Adapter 暴露原生 compaction 后再增加对应 opaque 状态续传。
5. Planner 与 Todos 已作为控制工具和 JSONL 事件实现；下一步按实际任务增加基础 Trace。
6. 出现可验证的跨 session 需求后增加 Long-term Memory。
7. Tool/Skill 候选过大且检索效果可验证时接入 RAG；它与 Memory 都成为真实消费者后，再提取通用 Retrieval package。

不为未出现的第二个消费者预建 `protocol`、`shared`、`planner`、`memory`、`retrieval` 或 `observability` package。
