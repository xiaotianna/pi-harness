# 前端对话学习规则

每次使用本 Skill 时完整阅读本文件。把这里维护为精简的规则账本，不要写成对话历史或变更日志。

## 记录格式

每条规则必须包含 ID、状态、范围、规则、依据和原因。状态只使用 `active`、`promoted` 或 `superseded`。只转述与规范有关的依据，不保存敏感信息或无关用户内容。

## 规则记录

### WEB-001

- 状态：`active`
- 范围：Provider 图标
- 规则：为 `kimi-coding` 直接渲染 `Kimi` 或 `Kimi.Color` SVG；不要使用 `Kimi.Avatar`，也不要仅为显示图标添加 Avatar 风格 wrapper。
- 依据：用户在修正 Provider 图标对齐时明确拒绝 `Kimi.Avatar`，要求直接使用 Kimi 图标。
- 原因：直接 SVG 与其他 Provider 图标拥有一致的盒模型，并避免隐藏的布局依赖。

### WEB-002

- 状态：`promoted`
- 范围：现有 Web UI
- 规则：修改行为或修复组件使用时，保持当前整体 UI 和组件语言；没有明确要求时，不把局部修正扩大为重设计。
- 依据：用户在要求建立前端规范 Skill 时明确表示当前前端 UI 已基本满意。
- 原因：后续工作应提升一致性，而不是抹掉已经确认的视觉方向。
- 已提升至：`SKILL.md` 的执行流程和样式规范。

### WEB-003

- 状态：`active`
- 范围：Provider OAuth 工作流弹窗
- 规则：保持每个 OAuth 步骤紧凑并本地化 Provider prompt；未开始、初次登录、重新登录和准备中等单一操作或纯状态反馈在弹窗内容区居中，多操作步骤统一放在一个靠右操作行，步骤活动期间不再渲染第二个弹窗级取消操作。状态包含授权地址时，应把用户手势创建的授权窗口自动导航到该地址，并保留显式的“打开授权页面”操作作为弹窗拦截兜底。
- 依据：用户拒绝了直接暴露上游英文、操作分散和重复取消的布局，随后明确要求单一 OAuth 操作及准备中状态反馈居中，并指出手动授权码步骤缺少前往授权页面的路径。
- 原因：居中的单一操作能形成明确焦点，统一操作行避免层级混乱，而自动导航配合显式入口可确保授权状态始终可操作。

### WEB-004

- 状态：`promoted`
- 范围：Skill 职责
- 规则：本 Skill 必须覆盖完整前端工程规范，组件使用规范只是其中一部分；正文和规则资料使用中文。
- 依据：用户明确要求把 Skill 改为中文，并把范围从组件约束扩大到完整前端规范。
- 原因：Skill 名称、触发描述和内容范围应准确反映项目实际使用方式。
- 已提升至：`SKILL.md`、`project-map.md` 和 Skill 元数据。

### WEB-005

- 状态：`promoted`
- 范围：代码与协议复用
- 规则：新增常量、枚举、类型、协议或工具函数前先全仓搜索并复用已有实现；受模块边界限制时，由原所有者提供最小安全导出，不在消费者中复制。API 边界必需的运行时校验 Schema 除外。
- 依据：用户指出 Web 重复定义了 runtime 已有的 `HarnessEventType`，并明确要求将“已有代码或枚举不要重写”加入项目规范。
- 原因：单一来源可以避免 runtime、daemon 与 Web 之间发生协议漂移。
- 已提升至：仓库 `AGENTS.md`、`SKILL.md` 和 `project-map.md`。

### WEB-006

- 状态：`active`
- 范围：对话输入与模型切换
- 规则：Agent 运行期间消息输入框保持可编辑，“+”菜单保持可打开；尚未接入的能力只禁用对应菜单项，不禁用整级入口。模型切换保持禁用直到 run 进入终态，并显示禁用鼠标样式。
- 依据：用户明确要求运行期间仍能输入，同时要求模型切换等待停止后恢复并提供禁用鼠标反馈；随后明确指出“+”入口不应被禁用。
- 原因：用户可以提前准备下一条消息，同时避免活动 run 中途改变模型配置。

### WEB-007

- 状态：`superseded`
- 范围：消息操作与失败状态
- 规则：用户消息在气泡尾部稳定显示复制操作；助手消息操作使用复制、重新生成、点赞和点踩，不使用无明确操作的更多菜单；run 失败使用语义化错误提示呈现。
- 依据：用户根据真实对话界面明确指出用户消息缺少复制、助手消息更多菜单应替换为点赞和点踩、裸错误文本观感不佳，并在后续检查中要求恢复未显示的消息按钮。
- 原因：常用操作应直接可见，失败状态需要明确层级和可访问语义。
- 替代规则：`WEB-008`

### WEB-008

- 状态：`active`
- 范围：Markdown 消息与消息操作
- 规则：消息操作作为气泡下方独立操作行，不覆盖正文；有 hover 能力时默认隐藏，仅在悬停当前整条消息或键盘聚焦其操作时显示，触屏设备保持可见。同一 run 内只在用户可见的 AI turn 正常结束后，把操作挂到最后一条助手消息，不跟随每个 `message.completed` 或内部模型 turn 渲染。助手 Markdown 消息只组合 `ChatMessage.Assistant`、`ChatMessage.Body`、`ChatMessage.Content` 和 `Markdown`，不渲染头像或媒体；run 失败继续使用语义化错误提示呈现。
- 依据：用户明确要求 Markdown 消息使用 HeroUI Pro `ChatMessage` 的核心消息部分，并连续纠正了消息操作的位置、显示时机，以及自动续轮时操作只能出现在最终 AI turn 结束处。
- 原因：沿用 Pro 组件的消息级 hover 状态，避免操作覆盖正文或在非当前消息上持续造成视觉干扰；以 run 终态识别用户可见的 AI turn，可以避免把内部续轮的单条消息完成误当成最终回复，同时保留键盘与触屏可用性。

### WEB-009

- 状态：`active`
- 范围：侧栏 Session 操作
- 规则：侧栏 Session 条目保留尾部 `…` 更多操作入口，并提供真实可用的重命名与归档操作；不要与消息操作栏的更多按钮混淆。
- 依据：用户明确澄清缺失的是侧栏对话条目的 `…` 菜单，其中需要重命名和归档。
- 原因：Session 管理属于侧栏条目上下文，操作入口和持久化能力必须同时存在。

### WEB-010

- 状态：`promoted`
- 范围：辅助函数与 Agent Prompt 归属
- 规则：与业务无关的通用辅助能力使用项目已有第三方库并放入所属模块 `utils`；业务相关的判断、解析和转换辅助函数同样归入所属模块 `utils`；模型和 Agent Prompt、Prompt 片段及协议标记统一放入 `prompts`。
- 依据：用户明确要求该约束同时适用于后端、前端和 packages，并指出 Runtime 中对象判断、内部消息判断和续轮 Prompt 的职责归属错误。
- 原因：统一归属可以避免业务文件重复实现基础能力，也能防止 Prompt、协议和编排职责再次混杂。
- 已提升至：仓库 `AGENTS.md` 和本 Skill 的文件与导出规范。

### WEB-011

- 状态：`active`
- 范围：侧栏工作区折叠状态
- 规则：持久化用户对各工作区的展开或折叠选择，桌面与移动侧栏共享状态；未保存偏好的新工作区默认展开。空工作区仍允许展开，并显示明确的空状态反馈。
- 依据：用户明确指出工作区折叠状态不能在每次初始化时重置为关闭。
- 原因：折叠属于跨初始化保留的纯 UI 偏好；保存折叠项可同时保留用户选择，并让异步加载或新增工作区沿用默认展开行为。

### WEB-012

- 状态：`active`
- 范围：本地工作区添加与会话绑定
- 规则：添加工作区时由 daemon 打开操作系统目录选择器并持久化校验后的真实路径；Web 使用工作区 ID 创建会话，不把浏览器文件选择结果或客户端路径作为工作区事实来源。侧栏与新对话工作区菜单复用同一添加流程；点击某个工作区行尾的“+”时，先把该工作区设为新对话的项目选择，再进入新对话页。工作区选择菜单中的名称固定为单行，超出可用宽度时省略。侧栏工作区条目为操作区预留空间并提供 `…` 菜单，菜单依次包含编辑、按操作系统命名的目录显示操作和移除项目；移除直接执行，不展示破坏性确认，只隐藏引用并保留本地文件与会话，再次添加同一目录时恢复原会话。
- 依据：用户明确要求选择本地目录，并让后端记录真实目录位置供后续工作区内容操作使用；随后明确指出软移除不是破坏性操作，不需要二次确认，并要求侧栏工作区“+”同步新对话的项目选择。
- 原因：浏览器目录选择无法提供可信绝对路径；由本地 daemon 持有真实路径，才能让后续文件与 Shell 能力安全绑定不可变工作区边界。工作区内的新对话入口必须保留其目录上下文；软移除可恢复且不删除数据，额外确认只会增加操作阻力。

### WEB-013

- 状态：`active`
- 范围：Tooltip 交互
- 规则：Tooltip 移出触发器后立即开始关闭，不保留额外关闭延迟；通过 HeroUI 全局主题变量统一控制，不在各调用点重复配置。
- 依据：用户明确指出 Tooltip 消失过慢会影响连续操作。
- 原因：操作型 Tooltip 在指针离开后继续停留会遮挡界面，并干扰相邻控件的快速操作。

### WEB-014

- 状态：`active`
- 范围：工作区排序
- 规则：工作区目录允许在侧栏拖拽调整顺序，并提供键盘等价操作；拖拽浮层保持为只含文件夹图标和名称的紧凑圆角条目，插入位置使用带起点圆点的强调色横线。排序由 daemon 持久化到本地 SQLite，Web 只更新 Query 缓存，不写入 `localStorage`。
- 依据：用户明确要求目录支持拖拽排序，并确认顺序应保存在本地文件而不是浏览器存储；随后指出浏览器默认拖拽快照不符合项目风格，并指定参考紧凑浮层与横线指示器。
- 原因：工作区顺序属于跨浏览器初始化保留的本地应用数据，应与工作区引用使用同一事实来源；精简的浮层和明确插入线能保留上下文，同时避免复制整行操作区造成视觉噪声。

### WEB-015

- 状态：`active`
- 范围：侧栏工作区状态
- 规则：当前上下文所属工作区的文件夹图标使用强调色；其他工作区图标使用 muted 灰色。已存在的会话按 Session 的工作区判断；尚未创建 Session 的新对话按输入器当前选择的工作区判断。展开状态只切换文件夹开合图标，不改变状态颜色。
- 依据：用户明确要求当前目录下的对话对应蓝色文件夹图标，其他目录保持灰色；随后指出新对话即使尚无 Session，也已经属于输入器所选工作区，应显示相同的蓝色状态。
- 原因：颜色应表达当前上下文的目录归属，是否已经产生消息或 Session 不影响归属；文件夹开合仅表达结构展开状态，二者不能混用。

### WEB-016

- 状态：`superseded`
- 范围：助手 Markdown 流式渲染
- 规则：助手 Markdown 使用 Streamdown，并将活动回复的流式状态传给 `isAnimating`；启用内容动画和块状 caret，静态消息关闭动画状态。
- 依据：用户明确指出当前 Markdown 不是流式渲染，并指定用 Streamdown 的动画与 caret 能力替换现有 Markdown 组件。
- 原因：Streamdown 能在增量内容尚不完整时稳定解析 Markdown，并只为当前活动回复呈现流式反馈。
- 替代规则：`WEB-017`

### WEB-017

- 状态：`active`
- 范围：助手 Markdown 与会话滚动
- 规则：助手回复使用 HeroUI Pro `Markdown` 的 memoized block 流式渲染。会话内容增长时，距离底部不超过 96px 自动跟随；超过阈值后保持用户阅读位置，并保留显式滚动到底部操作。
- 依据：用户基于 HeroUI Pro Markdown 文档确认恢复项目原组件，并明确要求 AI 输出根据底部距离阈值决定是否跟随滚动。
- 原因：按块更新可保留项目既有 Markdown 视觉；滚动阈值兼顾持续查看最新输出与向上阅读历史消息。

### WEB-018

- 状态：`promoted`
- 范围：加载状态语义
- 规则：AI 等待与生成状态统一使用 AICSS `Orbs` S2；骨架屏只用于页面数据请求期间，不用于模型生成、工具执行或其他 AI 活动状态。
- 依据：用户明确将 Orbs S2 声明为统一规范，并要求页面数据加载使用骨架屏。
- 原因：区分 AI 活动与数据请求，避免同一种加载反馈表达不同语义。
- 已提升至：`project-map.md` 的组件场景映射。

### WEB-019

- 状态：`active`
- 范围：会话消息渲染模块
- 规则：`ThreadMessage` 保持稳定目录入口；消息渲染策略组合和各独立消息组件分别放入 `components/thread-message/` 内的独立文件。
- 依据：用户明确要求拆分原有单文件中的 `MESSAGE_RENDER_STRATEGIES` 组合与每个独立组件。
- 原因：消息类型持续增加时，独立模块可以缩小单文件职责和改动范围。

### WEB-020

- 状态：`active`
- 范围：工具审批交互
- 规则：待处理的工具审批固定显示在会话底部并覆盖消息输入器；消息时间线中的 Tool 只呈现等待审批等工具状态，不在消息内重复展示审批详情或确认操作。
- 依据：用户明确要求参照 Codex 将审批放到底部输入区，并指出现有消息内审批卡片只应保留工具状态。
- 原因：审批是当前必须处理的会话级交互，覆盖输入器能形成唯一操作焦点，同时避免消息流与底部区域重复提供确认入口。

### WEB-021

- 状态：`active`
- 范围：列表项异步开关
- 规则：列表项共用 mutation 时，开关的 pending、disabled 等可见状态必须按当前操作项 ID 限定；受控开关应立即乐观更新 Query 缓存，用服务端响应校准，失败时只回滚当前项，不通过整列表失效刷新完成切换。
- 依据：用户指出切换某个 Provider 的 Switch 时其他 item 也会刷新，并在限定 disabled 状态后进一步反馈开关仍会闪烁。
- 原因：受控开关若等待请求完成后重拉列表，会经历旧值回弹和新值再次切换；局部乐观更新可以保持即时反馈并避免无关控件闪动。

## 维护规则

- 新规则使用下一个数字 ID。
- 反馈只是细化范围或措辞时，直接更新已有条目。
- 新反馈替代旧规则时，把旧条目标记为 `superseded` 并添加“替代规则：WEB-XXX”，不要静默删除冲突历史。
- 规则已经进入 `SKILL.md` 或 `project-map.md` 时，标记为 `promoted`。
- 只记录足以改变未来前端实现选择的具体规则。
