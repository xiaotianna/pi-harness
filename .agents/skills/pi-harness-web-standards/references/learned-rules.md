# 前端对话学习规则

每次使用本 Skill 时完整阅读本文件。把这里维护为精简的规则账本，不要写成对话历史或变更日志。

## 记录格式

每条规则必须包含 ID、状态、范围、规则、依据和原因。状态只使用 `active`、`promoted` 或 `superseded`。只转述与规范有关的依据，不保存敏感信息或无关用户内容。

## 规则记录

### WEB-001

- 状态：`active`
- 范围：Provider 图标
- 规则：为 `kimi-coding` 直接渲染 `Kimi` 或 `Kimi.Color` SVG；不要使用 `Kimi.Avatar`，也不要仅为显示图标添加 Avatar 风格 wrapper。
- 依据：用户在修正 Provider 图标对齐时明确拒绝 `Kimi.Avatar`，要求直接使用 Kimi 图标。
- 原因：直接 SVG 与其他 Provider 图标拥有一致的盒模型，并避免隐藏的布局依赖。

### WEB-002

- 状态：`promoted`
- 范围：现有 Web UI
- 规则：修改行为或修复组件使用时，保持当前整体 UI 和组件语言；没有明确要求时，不把局部修正扩大为重设计。
- 依据：用户在要求建立前端规范 Skill 时明确表示当前前端 UI 已基本满意。
- 原因：后续工作应提升一致性，而不是抹掉已经确认的视觉方向。
- 已提升至：`SKILL.md` 的执行流程和样式规范。

### WEB-003

- 状态：`active`
- 范围：Provider OAuth 工作流弹窗
- 规则：保持每个 OAuth 步骤紧凑并本地化 Provider prompt；未开始、初次登录、重新登录和准备中等单一操作或纯状态反馈在弹窗内容区居中，多操作步骤统一放在一个靠右操作行，步骤活动期间不再渲染第二个弹窗级取消操作。状态包含授权地址时，应把用户手势创建的授权窗口自动导航到该地址，并保留显式的“打开授权页面”操作作为弹窗拦截兜底。
- 依据：用户拒绝了直接暴露上游英文、操作分散和重复取消的布局，随后明确要求单一 OAuth 操作及准备中状态反馈居中，并指出手动授权码步骤缺少前往授权页面的路径。
- 原因：居中的单一操作能形成明确焦点，统一操作行避免层级混乱，而自动导航配合显式入口可确保授权状态始终可操作。

### WEB-007

- 状态：`superseded`
- 范围：消息操作与失败状态

- 依据：用户根据真实对话界面明确指出用户消息缺少复制、助手消息更多菜单应替换为点赞和点踩、裸错误文本观感不佳，并在后续检查中要求恢复未显示的消息按钮。
- 原因：常用操作应直接可见，失败状态需要明确层级和可访问语义。
- 替代规则：`WEB-008`

### WEB-008

- 状态：`active`
- 范围：Markdown 消息、消息操作与失败状态
- 规则：消息操作作为气泡下方独立操作行，不覆盖正文；有 hover 能力时默认隐藏，仅在悬停当前整条消息或键盘聚焦其操作时显示，触屏设备保持可见。消息完成时间复用操作行的相同显隐规则，以本地 `HH:mm`、常规字重和区别于操作图标的更弱颜色展示；用户消息时间位于操作图标左侧，AI 只在最终消息的操作图标右侧展示一次。同一 run 内只在用户可见的 AI turn 正常结束后，把操作挂到最后一条助手消息，不跟随每个 `message.completed` 或内部模型 turn 渲染。助手 Markdown 消息只组合 `ChatMessage.Assistant`、`ChatMessage.Body`、`ChatMessage.Content` 和 `Markdown`，不渲染头像或媒体。所有助手消息的 `ChatMessage.Body` 不保留 Pro 默认的尾部内边距，让正文、变更摘要和操作区使用完整可用宽度。run 失败使用 assistant-ui `ErrorState` 的结构与 HeroUI danger 语义色呈现，占满消息内容区，只显示标题和错误详情。
- 依据：用户明确要求 Markdown 消息使用 HeroUI Pro `ChatMessage` 的核心消息部分，并连续纠正了消息操作的位置、显示时机，以及自动续轮时操作只能出现在最终 AI turn 结束处；随后指定 run 失败状态使用 assistant-ui `ErrorState`，保留 HeroUI 色彩和精简内容，并要求宽度占满消息内容区；之后通过截图明确要求移除助手消息 Body 的尾部内边距；本次要求用户与 AI 消息结束后在操作行展示时间，并指定 hover 显示、两侧位置、弱化颜色、常规字重及 AI 只显示最终时间。
- 原因：沿用 Pro 组件的消息级 hover 状态，避免操作与时间覆盖正文或在非当前消息上持续造成视觉干扰；以 run 终态识别用户可见的 AI turn，可以避免把内部续轮的单条消息完成时间误当成最终回复，同时保留键盘与触屏可用性；移除共享 Body 的尾部预留可让所有助手内容使用一致的完整宽度，独立错误展示原语则保持失败反馈一致并充分利用消息空间。

### WEB-009

- 状态：`active`
- 范围：侧栏 Session 操作
- 规则：侧栏 Session 条目保留尾部 `…` 更多操作入口，并提供真实可用的重命名与归档操作；归档只隐藏侧栏条目并保留 Session 索引与 JSONL，在设置的“已归档”中按 Workspace 分组记录，并允许恢复；Workspace 分组标题固定单行，超出可用宽度时省略。不要与消息操作栏的更多按钮混淆。
- 依据：用户明确澄清缺失的是侧栏对话条目的 `…` 菜单，其中需要重命名和归档；后续进一步要求归档不能删除，需要在设置中按 Workspace 记录，并通过截图明确归档列表中的 Workspace 标题只展示一行。
- 原因：Session 管理属于侧栏条目上下文，操作入口和持久化能力必须同时存在；可恢复的设置记录让归档与删除保持清晰区别。

### WEB-010

- 状态：`promoted`

- 原因：统一归属可以避免业务文件重复实现基础能力，也能防止 Prompt、协议和编排职责再次混杂。
- 已提升至：仓库 `AGENTS.md` 和本 Skill 的文件与导出规范。

### WEB-012

- 状态：`active`
- 范围：本地工作区添加与会话绑定
- 规则：添加工作区时由 daemon 打开操作系统目录选择器并持久化校验后的真实路径；Web 使用工作区 ID 创建会话，不把浏览器文件选择结果或客户端路径作为工作区事实来源。侧栏与新对话工作区菜单复用同一添加流程；点击某个工作区行尾的“+”时，先把该工作区设为新对话的项目选择，再进入新对话页。工作区选择菜单中的名称固定为单行，超出可用宽度时省略。侧栏工作区条目为操作区预留空间并提供 `…` 菜单，菜单依次包含编辑、按操作系统命名的目录显示操作和移除项目；移除直接执行，不展示破坏性确认，只隐藏引用并保留本地文件与会话，再次添加同一目录时恢复原会话。
- 依据：用户明确要求选择本地目录，并让后端记录真实目录位置供后续工作区内容操作使用；随后明确指出软移除不是破坏性操作，不需要二次确认，并要求侧栏工作区“+”同步新对话的项目选择。
- 原因：浏览器目录选择无法提供可信绝对路径；由本地 daemon 持有真实路径，才能让后续文件与 Shell 能力安全绑定不可变工作区边界。工作区内的新对话入口必须保留其目录上下文；软移除可恢复且不删除数据，额外确认只会增加操作阻力。

### WEB-015

- 状态：`active`
- 范围：侧栏工作区状态
- 规则：当前上下文所属工作区的文件夹图标使用强调色，收起和展开图标都保留同色系的浅色内部填充；其他工作区图标使用 muted 灰色。已存在的会话按 Session 的工作区判断；尚未创建 Session 的新对话按输入器当前选择的工作区判断。展开状态只切换文件夹开合图标，不改变状态颜色。Gravity UI 的文件夹轮廓与对应 Fill 图标成对叠加，不能因其内部 path 固定 `fill` 而丢失软色填充。
- 依据：用户明确要求当前目录下的对话对应蓝色文件夹图标，其他目录保持灰色；随后指出新对话即使尚无 Session，也已经属于输入器所选工作区，应显示相同的蓝色状态；替换为 Gravity UI 图标后又明确要求收起和展开目录都恢复浅蓝内部填充。
- 原因：颜色应表达当前上下文的目录归属，是否已经产生消息或 Session 不影响归属；文件夹开合仅表达结构展开状态，二者不能混用；分别叠加 Fill 与轮廓图标可保留 Gravity UI 几何，同时恢复原有的软色层级。

### WEB-016

- 状态：`superseded`

- 规则：助手 Markdown 使用 Streamdown，并将活动回复的流式状态传给 `isAnimating`；启用内容动画和块状 caret，静态消息关闭动画状态。

- 替代规则：`WEB-017`

### WEB-017

- 状态：`active`
- 范围：助手 Markdown 与会话滚动
